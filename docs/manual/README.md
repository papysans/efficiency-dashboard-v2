# 提效看板 · 系统说明书（交付置信源）

> 本说明书是**面向客户交付的权威说明文档（置信源）**。它逐页面、逐字段说明看板上每个数字的**含义、数据来源、计算口径、算法公式、边界处理**，并为每一条结论标注代码出处（`文件:行号`），以便技术对接方逐条复核。汇报时遇到的任何"这个数为什么是这样"，都应能在本说明书内找到答案。

---

## 一、阅读对象与定位

| 读者 | 关注点 | 在本说明书中看 |
|---|---|---|
| 客户汇报人 | 每个指标怎么解释、异常值怎么答 | 各页面的「字段速查表」+「边界与常见质疑应答」 |
| 客户技术对接方 | 数字怎么算出来的、能否复核 | 「算法白皮书」+ 各字段的「算法与出处」 |
| 交付/实施工程师 | 口径变更、字段映射 | 「附录：字段字典 / 口径变更记录」 |

定位口径：**技术对接层**。算法部分给出真实公式 + 字段映射 + 代码出处，不停留在大白话；同时每个指标配一句业务解释，供汇报直接引用。

```
docs/manual/
├── README.md                      ← 本文（总入口 + 约定 + 页面清单）

├── 01-算法白皮书.md                ← 所有页面共享的算法：两种口径 / 工时 / kNN / LLM / 融合 / Episode / Outlier / 资格 / 治理
├── pages/                          ← 逐页面说明书（23 页，按模块分册）
│   ├── 需求详情-NeedDetail.md       ← 【样板页 · 已完成】
│   └── …
├── 03-数据质量与常见质疑应答.md     ← 极端值/0/空/隐藏/资格率 的统一解释（汇报防弹衣）
├── 04-附录-字段字典与口径变更.md    ← DB列↔展示字段全量字典 + 口径/版本变更记录
└── _internal/                      ← 【不交付客户】考据存疑、待修代码、口径待核
```

> **交付边界**：交付客户时仅打包 README + `00`~`04` + `pages/`；`_internal/` 为内部备忘，不随交付。

各页面文档**不重复**算法推导，凡涉及共享算法处一律以 `→ 见《01-算法白皮书》§X` 交叉引用，保证全书口径单一、不自相矛盾。

## 三、文档约定

1. **出处标注**：每条可复核的结论后标 `文件路径:行号`（如 `efficiency_v2_fusion.go:204`）。行号基于 `feat/needs-user-search-multi-caliber` 分支当前快照；版本演进后以「附录」的变更记录为准。
2. **口径符号**：
   - 【日历口径】= 自然时间跨度（开发开始→结束，扣除长搁置），回答"这个需求花了多少天"。
   - 【人力/活跃口径】= 实际投入的活跃工作分钟，回答"花了多少人·分钟"。
   - 【估算口径】= 采集未覆盖部分由算法补估（思考/执行为粗略估算，验证当前采集未覆盖）。
   - 三种口径**不可混用**，每个工时/提效字段都标注它属于哪种口径。
3. **空态符号**：页面用 `-`（半角，普通空值）与 `—`（全角，U+2014，表示"该口径采集未覆盖"，主要出现在"验证"字段）区分，本说明书沿用此区分并解释成因。
4. **截图**：每页配真实运行截图并对关键字段做标注（截图来自本地全栈运行的真实数据，非 mock）。
5. **诚实原则**：凡"看起来像 bug、实为数据限制或设计选择"的点，一律在该页「边界与常见质疑应答」中正面写清触发条件与代码出处，不回避。

## 五、生产流程（内部）

本说明书采用「subagent 并行考据 → 主控整理校验 → codex 终审」的流水线：
1. 每页派一个 subagent，端到端追踪「前端渲染 → API 契约 → 后端 SQL → 算法公式」四层，返回带 `文件:行号` 的结构化考据。
2. 主控将考据整理为客户可读文档，交叉引用算法白皮书，并把存疑项回流给用户决策。
3. 全书完成后 `codex review` 终审，核对每条出处与口径是否准确。
