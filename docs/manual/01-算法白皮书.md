## 0. 总览：一条数据从采集到指标，经过哪些阶段

```
 原始采集（会话 conversation / 提交 commit / 任务 task）
        │
        ▼
 ① 数据治理 governance        ── 写侧打标，不删数据；脱敏、排除 bot/纯文档、巨型 commit 软上限、重放去重、merge 归零
        │   产出：commits.excluded_flag / effective_diff_lines（统一有效行数入口）
        ▼
 ② 需求边界与 Episode 分桶     ── 把会话+提交聚合成"需求 Need"，定边界来源/置信、按长搁置切 Episode
        │   产出：need_id / boundary_source / boundary_confidence / dev_start~dev_end
        ▼
 ③ 工时口径计算               ── 日历口径（自然周期）& 人力/活跃口径（去重人·分钟 + 未覆盖补估）
        │   产出：total_calendar_min / total_active_work_corrected_min
        ▼
 ④ 阶段划分                   ── 把会话事件分到 思考/执行/验证/其他
        │   产出：think/exec/verify/other 分钟、stage_confidence
        ▼
 ⑤ 三路工时基线              ── 古法算法基线 A / 相似锚点 kNN（B）/ LLM 估算（C），各自估"不用 AI 要多久"
        │   产出：baseline_algo / baseline_anchor_knn / baseline_llm
        ▼
 ⑥ 基线融合                  ── 三路加权融合成"传统人力预估"，再换算"传统周期预估"，得两套提效比
        │   产出：baseline_fused_work_min / baseline_calendar_min / efficiency_ratio / work_efficiency_ratio
        ▼
 ⑦ 置信分档 & ⑧ 异常隔离      ── 给提效比定置信档；极端值打异常标签（只隔离不改数）
        ▼
 ⑨ 资格判定                  ── 决定该需求是否计入提效统计（coverage_eligible）
        │
        ▼
   前端各页面展示
```

> 术语：**Need（需求）**=一段被识别出边界的连续开发工作；**Session（会话）**=一次 AI 编程会话；**Commit（提交）**=一次代码提交。三者多对多聚合成 Need。

> ⚠️ **全局须知：系统并存两套提效比口径，不同页面用不同口径，数值不可横向比较。**
> - **V2 融合口径（小数）**：本篇 §1–§9 描述的就是这套，用于 **需求各页 / 用户列表·详情 / 总览 / 部门成员**。前端小胶囊 `RatioPill`，把小数 ×100 显示（0.25 → 25%）。
> - **V1 古法口径（百分比）**：用于 **仓库列表·详情 / 项目列表·详情 / 用户组 / 提交详情**。前端小胶囊 `PercentPill`，数值本身就是百分比、不再 ×100（300 → 300%）。详见 **§12**。
> 把一个 V2 的 `3.0`（= 300%）和一个 V1 的 `300`（= 300%）放在一起比是错误的；务必先看该页属于哪套口径（§12 有逐页对照表）。

## 1. 数据治理 Governance（阶段①）

**定位**：在所有提效计算之前先跑的写侧清洗。**只打标记、改有效行数，不删原始数据**，可追溯、可复原。改治理名单后重跑 efficiency-v2 即全口径生效。

- 总入口 `ApplyCommitGovernance`（`kbcli/internal/governance/pass.go:19`），由 efficiency-v2 主流程最先调用（`kbcli/cmd_efficiency_v2.go:122`）。
- 由 **5 个有序子 pass** 组成，顺序有依赖（`governance/pass.go:14-34`）：

| 序 | 子 pass | 作用 | 出处 |
|---|---|---|---|
| 1 | repo 地址脱敏 | 剥掉仓库地址里内嵌的明文 token/密码 | `sanitize.go:55` |
| 2 | 身份治理 | 排除 bot/测试/越权身份的提交 | `identity.go:85` |
| 3 | 纯文档 commit 排除 | 整条仅改文档的提交不计入代码量 | `doconly.go:74` |
| 4 | commit 规则 | 软上限 + comment 降权 + 重放去重 | `commitrules.go:44` |
| 5 | merge 治理 | merge 提交的 diff 不计交付 | `merge.go:30` |

### 1.1 有效行数统一入口（治理→全口径生效的关键）
所有下游口径的代码行数都走同一个方法 `Commit.GetEffectiveDiffLines()`（`core/models/models.go:124-132`）：
```
若 excluded_flag = true        → 返回 0
否则若 effective_diff_lines 有值 → 返回该折算值
否则                            → 返回原始 diff_lines
```
这一个入口同时喂给：古法基线 exec 行数（`efficiency_v2_baseline_algo.go:207`）、need 聚合的 `changed_loc`/`ai_covered_loc`/`uncovered_loc`（`efficiency_v2_need_aggregate.go:354-365`）、silica 加权（`:428`）。**所以治理只要打一次标，LOC / AI 代码占比 / 古法基线全部自动归零或折算**，无需各口径单独处理。聚合 SQL 另加 `WHERE excluded_flag = false` 作双保险（`efficiency_v2_need_aggregate.go:55`）。

### 1.2 各规则与阈值

- **巨型 commit 软上限 softcap**：`diff_lines > 3000` 时把有效行数截到 3000（**严格大于**，等于不截）。默认 `diff_lines_softcap = 3000`，置 0 关闭。出处 `commitrules.go:160-166`，默认 `config.go:67`。作用于净行数标量。
- **comment 降权**：提交说明命中降权正则 → 有效行数 `× factor`（多条命中取最小 factor）。默认正则 `(?i)^[\[\(]?(merge|sync|format|style|scaffold|init)\b`、`factor=0.2`（`config.go:68-72`）。**行首锚定**是为避免句中词误伤（见 §11 误伤史）。出处 `commitrules.go:167-178`。
- **纯文档 commit 排除**：`touched_files` 非空且**每个**文件后缀都是文档后缀 → 整条 `excluded_flag=true`、`excluded_reason=doc_only_commit`。默认后缀 `.md / .mdx / .markdown`（大小写不敏感，可经 `governance.yaml` 配）。**故意不含 `.txt`**（requirements.txt/CMakeLists.txt 等多非文档）。出处 `doconly.go:37-57`，默认 `config.go:74`。
- **重放去重 replay**：同 `(user_id, 归一仓库地址, 去空格提交说明, diff_lines)` 的重复提交，按时间保最早，其余 `replay_of=最早id` 且有效行数归 0。仅 `diff_lines>100 且 提交说明长度>5` 的提交参与（避免误判小改动）。默认开启。出处 `commitrules.go:113-151`，常量 `:23-25`。
- **merge 归零**：提交说明匹配 `(?i)^merge\s+(branch|pull request|remote|tag|commit)\b` → `is_merge=true` → 有效行数归 0（merge 的 diff 不算交付）。出处 `merge.go:17,30-57`。
- **身份治理**：按优先级排除 内置 bot 邮箱正则 / 邮箱黑名单 / 邮箱通配 / git 名黑名单 / identity_map 越权 / user_id 黑名单，命中即 `excluded_flag=true`（reason 如 `identity:bot`）。被排除的 user 在 session/need 侧也整体过滤。出处 `identity.go:38-79`，注入 `cmd_efficiency_v2.go:128-130`。
- **仓库地址归一 canon**：统一 `git@`/`https`/带不带 `.git`/端口 等写法，让同一仓库的不同写法合并统计；同时剥掉地址里的 token。默认开启。出处 `canon.go:11-52`。

> 治理可配项清单见 §10.4 与《04-附录》。

## 2. 需求边界与 Episode 分桶（阶段②）

**定位**：把治理后的会话与提交聚合成"需求 Need"，确定每个 Need 的边界来源、置信、起止时间。主流程 `ResolveEfficiencyV2Needs`（`efficiency_v2_need_boundary.go:201-257`）。

### 2.1 边界来源与置信（5 级，优先级从高到低）
`efficiencyV2ResolveNaturalBoundary`（`efficiency_v2_need_boundary.go:462-489`）：

| 级别 | 触发条件 | boundary_source | boundary_confidence |
|---|---|---|---|
| 1 | 提取到 PR 号 | `lv1_pr` | high |
| 2 | 分支名非主干 | `lv2_branch` | high |
| 3 | 提取到 Issue 号（如 JIRA-123） | `lv3_issue` | medium |
| 4 | 触达文件 ≥ 2 | `lv4_cluster` | low（无时间则 very_low） |
| 5 | 兜底 | `lv5_orphan` | very_low |

- 主干分支（`main/master/develop/release` 及其前缀）不作分支边界，跌落到 issue/cluster/orphan（`:659-663`）。
- 边界唯一键 `boundary_key` 形如 `branch:{仓库}:{分支}` / `issue:{id}` 等；按 `来源+键` 分桶聚合。
- 不同分支 → 不同 `branch:` 键 → 落不同桶 → 成不同 Need。这就是"同一批工作切换分支后被拆成两个需求"的机制（无独立劈裂函数，是边界键的自然结果）。

### 2.2 起止时间与 Episode 切分
- `dev_start_ts` = 桶内所有候选（会话+提交）起点最小值，`dev_end_ts` = 终点最大值（`:532-537`）。晚于当前时刻的端点截到"现在"（纠正上游时区误标，`:542-549`）。
- **Episode 切分**：桶内候选按时间扫描，相邻活动间隙 **> 3 天（idle 阈值）** 即切成新段（`efficiencyV2SplitBucketEpisodes`，`:266-317`）。单段不改 need_id（兼容存量）；多段给每段 need_id 追加 `@YYYY-MM-DD` 后缀。
- `idle_threshold_days` 默认 3（`config.go:130-132`）。
- **集成流降级**：Episode 切完后仍跨度 > 7 天且贡献者 ≥ 3 的段，置信强降为 low（多人长周期集成流不作单需求提效，`:565-577`）。`max_need_span_days` 默认 30、`integration_flow_span_days` 默认 7、`integration_flow_min_contributors` 默认 3。

### 2.3 状态 status
候选自带 status 则继承；默认 `active`，**只要桶内有提交就升为 `merged`**（`:556-558`）。status 与置信共同决定资格（见 §9）。

## 3. 工时口径（阶段③）—— 两套口径，不可混用

系统对"实际花了多少"用两套口径并行衡量：

### 3.1 日历口径（自然周期）
`total_calendar_min` = `dev_end - dev_start`，**减去其中所有 > 3 天的长搁置**（`computeEfficiencyV2DevCalendarMinutes`，`efficiency_v2_need_aggregate.go:186-248`）。
- 含义：回答"这个需求从开始到结束经历了多少自然时间"。
- **包含周末、夜间、< 3 天的停顿**（设计有意，注释 `:180-185`），只扣超过 3 天的长停滞。
- 另有 `dev_duration_min` = `dev_end - dev_start` 的**原始毛跨度（未扣搁置）**（`efficiency_v2_need_boundary.go:617-619`）。二者口径不同：`total_calendar_min` 是分母，`dev_duration_min` 仅作展示。

### 3.2 人力 / 活跃口径
`total_active_work_corrected_min` = **去重活跃人·分钟 + 未覆盖补估**（`efficiency_v2_need_aggregate.go:380`）。
- **去重活跃人·分钟** `total_session_active_person_min`（`efficiencyV2NeedPersonMinutes`，`:286-332`）：按用户分组，对同一用户并行（时间窗重叠）的多个会话取活跃区间**并集封顶**，避免"一人同时开多个会话被重复计时"。默认开启（`parallel_session_union`，`config.go:221-224`）。
- **未覆盖补估** `estimate_uncovered_human_min`（`:528-541`）：采集未覆盖到的代码改动，按"代码行 ÷ 速率"折算成人工分钟。速率默认 ≈ 0.2083 行/分钟（即传统 100 行/人天 ÷ 480 分钟，约 4.8 分钟/行，`:23`）。

### 3.3 什么算"AI 覆盖" vs "未覆盖"（时间维度判定）
单个提交是否算被 AI 会话覆盖，**仅按时间判定**：提交时间是否落在某会话窗口 `[会话开始-30分钟, 会话结束+60分钟]` 内（`isEfficiencyV2CommitCovered`，`:493-503`；前后边距默认 30/60 分钟，`config.go:169-174`）。
- 落入 → 计入 `ai_covered_loc`；落外 → 计入 `uncovered_loc` 并触发未覆盖补估。
- **口径边界**：当前提交记录不带文件清单参与匹配，故覆盖判定是纯时间维度，`quality_signals.reason` 恒含 `covered_rule=temporal_only`（`:400`）。这会让"时间窗外但实际同属一次 AI 会话"的提交被算作未覆盖。

## 4. 阶段划分（阶段④）—— 思考 / 执行 / 验证 / 其他

把会话内事件分配到四个阶段，得到各阶段活跃分钟。

### 4.1 事件分类与状态机
- 事件先分 5 类：edit / verify / read / message / other（`ClassifyEfficiencyV2Event`，`efficiency_v2_stage.go:46-69`，按 edit→verify→read→message→other 顺序短路）。
- 再走状态机定阶段（`BuildEfficiencyV2SessionStageMetric`，`:239-261`，初始"思考"）：
  - other 类 → 记**其他**；
  - 该会话**从未出现 edit** → 所有非 other 事件一律记**思考**（思考是兜底承接，几乎总有值）；
  - 已有 edit 后：edit→进入**执行**、verify→进入**验证**、read/message→沿用当前阶段。
- 单事件时长推断：优先用显式起止；否则用"到下一事件的间隙"但仅当间隙 ≤ 5 分钟才采纳；再否则用类别默认时长（edit 30s / read 10s / verify 30s / other 10s / message 按 300 字/分钟）（`:73-86`，`config.go:154-167`）。

### 4.2 为什么"验证"阶段几乎恒为 0（重要口径边界）
验证阶段的产生**唯一依赖事件带"命令执行"文本**（go test / npm build 等，`:59-61`）。但当前采集的原始会话普遍不记录命令执行字段，事件归一化时该字段恒为空（`efficiency_v2_events.go:96-106`），因此验证分支几乎永不触发，`total_verify_min` 普遍为 0、前端显示为 `—`。
- **这是数据采集覆盖的结构性缺失，不是计算错误。** 思考/执行为粗略估算口径、有兜底所以总有值；验证待上游采集补齐命令事件后才有数据。

### 4.3 会话阶段置信 stage_confidence
per-会话取值：`high`（默认）/ `medium`（部分事件降级）/ `low`（全部降级或混入多会话）/ `very_low`（会话无任何事件）（`:171-279`）。降级=事件解析质量非 exact。注意这是**会话级**置信，与 §8 的需求级提效置信是两套体系。

## 5. 三路工时基线（阶段⑤）—— 各自估"不用 AI 要多久"

系统用三种独立方法估算"传统（不用 AI）完成同样产出需要的人力分钟"，互为印证。

### 5.1 古法算法基线（A）
按代码量与会话信号的工程经验公式估时（`efficiency_v2_baseline_algo.go:118-149`），三阶段相加（仅累加非空阶段）：
- **思考** = `用户字符数 × 0.02 + 读文件次数 × 5 + 对话轮数 × 5`，下限 5 分钟（`:185-187`，系数 `:49-56`）。真实数据里对话轮数是主信号。
- **执行** = `有效代码行 ÷ 0.2083 + 文件数 × 30`，下限 5 分钟（`:225-226`）。代码行先过滤 lock/生成文件（`package-lock.json`、`*.pb.go`、`*.gen.ts` 等，**不含文档**），再按"保留文件占比"折算（`:199-247,338-364`）。纯格式化提交直接压到下限。
- **验证** = `验证事件数 × 5 + 重试提示数 × 5 (+ 复审阅读估计 × 1)`，下限 5 分钟（`:267-273`）。

### 5.2 相似锚点 kNN（B / Method B）
用历史相似需求的真实工时来估当前需求（`efficiency_v2_baseline_knn.go:225-271`）：
- **锚点库**：经 `import-anchor` 命令从 CSV 母表导入（默认 `docs/data/efficiency_v2_anchor_set.csv`）。当前为团队 AI-Native 自报锚点。
- **相似度**：在需求特征向量（活跃工时量级 `log_work_min`、AI 代码占比 `ai_code_ratio` 等）上算欧氏距离，取最近 **k=5** 个锚点。
- **估值**：逆距离加权 `estimate = Σ(锚点工时 × w) / Σw`，权重 `w = 锚点权重 / (距离+1)`（`:254-265`）。
- 锚点工时在导入前已做尺度校准（对齐古法基线口径，校准系数烤进数据，不在代码内）。

### 5.3 LLM 估算（C）
大模型读取需求的结构化摘要后给出工时估计（`efficiency_v2_baseline_llm.go:169-213`）：
- **不传原始代码 diff / 对话原文**，只传结构化摘要（提交说明、任务标题、触达文件名、会话摘要、各阶段分钟、AI 占比等，`:62-109`）。
- 模型默认 `claude-3-5-sonnet`（可配），温度 0，要求严格 JSON 输出 `think/exec/verify/total/confidence/reason`。
- **禁用 / 调用失败 / 被限流（429）/ 返回非法** → `llm_total_min` 置空、reason 记 `llm:disabled` / `llm:call_failed` 等，该路不参与融合，前端基线表隐藏 LLM 行（`:170-229`）。仅 JSON 解析失败会重试一次，网络/限流不重试。

## 6. 基线融合与两套提效比（阶段⑥）

`ComputeEfficiencyV2Fusion`（`efficiency_v2_fusion.go:123`）。

### 6.1 融合
- **可用基线** = 非空且值 ≥ 0 的路（`:133-141`）。
- **加权融合**：默认权重 古法 0.30 / kNN 0.45 / LLM 0.25（`config.go:231-239`），**对实际可用的子集归一**（只有 1~2 路可用时分母是可用权重之和，非固定 1.0）：
  ```
  baseline_fused_work_min = Σ 基线值 × (权重 / 可用权重之和)
  ```
  （`:152-174`）
- **离散度 spread** = 可用基线的最大值 − 最小值（极差，非标准差，`:388-402`）。仅 1 路可用时 spread=0。
- 无任何可用基线 → 置信 `unknown`、reason `fusion:no_baselines`（`:146-150`）。

### 6.2 四个最终量
设 `density` 默认 0.25（团队工作密度）、`calib` 默认 1.0（日历标定）：

| 量 | 公式 | 出处 |
|---|---|---|
| 传统人力预估 | `baseline_fused_work_min`（上式） | `:174` |
| 传统周期预估 | `baseline_calendar_min = (fused / density) × calib` | `:200` |
| **日历提效** | `efficiency_ratio = (baseline_calendar_min − total_calendar_min) / total_calendar_min` | `:204` |
| **人力提效** | `work_efficiency_ratio = (baseline_fused_work_min − total_active_work_corrected_min) / total_active_work_corrected_min` | `:228` |

- 日历提效要求 `total_calendar_min > 0`，否则记 reason `fusion:missing_actual_calendar`（`:223-225`）——这与资格判定的零日历否决呼应（§9）。

### 6.3 提效比置信区间 band
当 spread > 0：以 fused ± spread/2 上下展开，换算成提效比上下界 `efficiency_band_low / high`（`:207-221`）。当 `spread/2 ≥ fused`（离散度吞没融合值）时不设下界，记 reason `band:spread_exceeds_fused`。前端"区间 X% ~ Y%"即此。

## 7. 置信分档 confidence_level（阶段⑦）

`classifyEfficiencyV2Confidence`（`efficiency_v2_fusion.go:281-320`）。按顺序短路判定，设 `离散比 = spread / fused`：

| 1 | 可用基线 = 0 | unknown |

| 9 | 以上都不命中 | high |

阈值默认值见 `config.go:175-189`。第 4~7 条要求对应字段有值才参与。需求级置信只产出 high/medium/low/unknown 四档。

## 8. 异常隔离 Outlier（阶段⑦）—— 只隔离，不改数

极端提效比通常源于一侧数据不完整（活跃工时偏小、日历偏短、或代码量含机器生成）。系统对极端样本**打异常标签并移出统计池，但不裁剪其数值**（`efficiency_v2_fusion.go:232-271`）：

| 异常类别 | 触发条件 | 打哪个标签 |
|---|---|---|
| 工作量异常 actual_to_baseline | 实际人力/融合基线 > 5 或 < 0.10 | `work_outlier_flag` |
| 日历异常 efficiency_ratio | 日历提效 > 10 或 < −2 | `calendar_outlier_flag` |
| 不可能行率 loc_rate | 净代码行/日历分钟 > 7（≈一天上万行，多为机器生成） | 两个标签都打 |

- 阈值默认值见 `config.go:205-219`。`outlier_flag = 任一口径异常`（`:271`）。
- **排除范围可配** `exclusion.scope`：默认三类全开 `[efficiency_ratio, loc_rate, actual_to_baseline]`；配空列表则全不隔离（极端值全计入）。出处 `config.go:250-269`。
- **关键**：异常只决定"是否从聚合中隐藏"，**单条数值原样保留**（注释 `:248-249,258`），所以详情页仍显示极端原值并配异常标签。

## 9. 资格判定 coverage_eligible（阶段⑨）—— 是否计入提效统计

分两阶段、三道关卡，任一否决即"未计入"：

1. **初判**（边界层，`efficiency_v2_need_boundary.go:607`）：`status = merged` 且 `boundary_confidence ∈ {high, medium}` → 初判"可计入"。即必须有交付物（有提交→merged）且边界可信（PR/分支/Issue 三类）。
2. **否决一：零日历**（聚合层，`efficiency_v2_need_aggregate.go:153-163`）：`total_calendar_min ≤ 0` → 改回"未计入"，reason `episode has deliverable but zero calendar`。无真实可测的日历分母（单提交/零跨度）不硬填估时，避免虚高比值。
3. **否决二：无会话（commit-only）**（聚合层，`:166-168`）：该需求下没有任何 AI 会话 → 改回"未计入"。只有提交、时间侧零上报，不构成可信分母。

> 这解释了"已 merged 却显示未计入"：初判通过后被零日历或 commit-only 否决。资格率偏低的主因是**采集完整度**（时间侧或交付侧缺一），非算法或治理可补。

## 11. 适用范围与口径边界（汇报须知）

本系统是**估算性度量**，用于反映 AI 编程的提效趋势与分布，不宜当作精确工时账。以下口径边界在汇报时应同步说明：

1. **"验证"阶段当前无数据**（§4.2）：采集未覆盖命令执行事件，验证分钟普遍为 0、显示 `—`。属采集覆盖缺失，待上游补齐。
2. **AI 覆盖按时间窗判定**（§3.3）：提交是否算 AI 覆盖仅按时间，不按文件内容比对，存在时间窗外同源提交被算未覆盖的情况。
3. **资格率受采集完整度制约**（§9）：缺时间侧或交付侧的需求被排除统计，资格率偏低主要反映上报完整度，而非真实提效低。
4. **极端值被隔离不被删除**（§8）：异常样本打标移出统计池但保留原值可查，确保总体口径不被个别不完整样本污染。
5. **三路基线为估算、互为印证**（§5）：古法基于工程经验系数，kNN 基于历史相似锚点，LLM 基于语义理解；融合降低单一方法偏差，但不等于精确测量。
6. **两套提效比口径并存、不可横向比较**（§12）：需求/用户/总览/部门用 V2 融合小数口径；仓库/项目/用户组/提交用 V1 古法百分比口径。两者数据源、公式、过滤层都不同，汇报时务必标明该页属于哪套口径。

## 12. V1 古法提效比口径（仓库 / 项目 / 用户组 / 提交页）

本系统早期（V1）以 **commit / task 的"古法工时估算"** 衡量提效，后期（V2）才引入 §1–§9 的需求级融合管线。当前两套并存，分别服务不同页面。本节说明 V1 口径，供仓库/项目/用户组/提交页查阅。

### 12.1 页面 → 口径 对照表（最重要）

| 页面 / 维度 | 提效比口径 | 前端胶囊 | 数据源 |
|---|---|---|---|
| 需求列表 / 需求详情 | **V2 融合（小数）** | RatioPill | needs 表 |
| 用户列表 / 用户详情 | **V2 融合（小数）** | RatioPill | user_productivity_v2 / needs |
| 总览 | **V2 融合（小数）** | RatioPill | needs 聚合 |
| 部门成员（组织树右栏） | **V2 融合（小数）** | RatioPill | needs 聚合 |
| 仓库列表 / 仓库详情 | **V1 古法（百分比）** | PercentPill | commits 表 |
| 项目列表 / 项目详情 | **V1 古法（百分比）** | PercentPill | commits + tasks 表 |
| 用户组详情 | **V1 古法（百分比）** | PercentPill | tasks + commits 按天 |
| 提交详情 | **V1 古法（百分比）** | PercentPill | commit 表 |
| 提交列表 / 工作目录详情 | 不展示提效比 | — | commits 表 |
| 平台 3 页 | 外部 chat 服务指标（非提效比） | — | 外部服务 |

> 注：仓库/项目页虽是 V1 口径，但其中**"AI 代码占比"列是 V2 needs 口径**（小数，RatioPill）——同一页两套口径并存，详见各页文档。

### 12.2 V1 核心公式 `CalcEfficiencyRatio`
`core/utils/calc.go:9-15`：
```
提效百分比 = (传统古法分钟 − 实际分钟) / 实际分钟 × 100   （保留 1 位小数）
```
- 任一边 ≤ 0 或实际为无穷 → 返回 0（`calc.go:10-12`）。
- **已 ×100，是百分比口径**：300 即 +300%（≈ 提速到 4 倍）。前端 `PercentPill` 直显不再 ×100。
- 人工调整优先 `CalcEfficiencyRatioManual`（`calc.go:16-30`）：传了 `*_manual` 值则覆盖算法值参与公式。

### 12.3 commit 级古法工时怎么来（写侧，kbcli）
- **传统预估 `commit_ancient_minutes`**（`kbcli/algo_estimator.go:8-17`）：`改动行数 ÷ 速率`，速率默认 ≈ 0.2083 行/分钟（传统 100 行/人天，≈4.8 分钟/行），下限 5 分钟。用的是原始 diff 全量行。
- **实际耗时 `commit_real_minutes`**（`kbcli/silica.go:559-588`）：`AI 会话耗时（关联 task 实际工时之和）＋ 残余传统编码耗时（未被 AI 指纹匹配的行再走上面的古法估时）`。

### 12.4 task 级古法工时
- **传统预估 `task_ancient_minutes`**（`kbcli/task.go:48-75`）：`(改动行数 ÷ 2 行每分钟) × 字数因子`，字数因子按用户输入字符在 [0.2, 1.0] 线性插值；结果裁剪到 `[max(5, 实际), 10×实际]`（故古法恒 ≥ 实际）。
- **实际耗时 `task_real_minutes`**（`kbcli/task.go:93-143`）：对话按时间排序，相邻间隔 ≤ 10 分钟合并为一个时间片，每片尾部 +5 分钟，各片时长求和。

> ⚠️ commit 与 task 的"每分钟行数"常量不同（commit 0.2083 vs task 2，差约 9.6 倍），二者都叫"古法"但不同源；组织维度同时汇总 task 与 commit 提效比时口径不齐。

### 12.5 读侧缺失工时的派生兜底
当 commit 的古法/实际分钟缺失（≤0），后端 `deriveCommitWorkMinutesBatch`（`backend/db.go:725-838`）实时补值：
1. **Need 平摊**：把该 commit 所属 Need 的 `baseline_fused_work_min`（→传统）与 `total_active_work_corrected_min`（→实际）按 commit 数等分。
2. **提交间隔法**：Need 未覆盖的，按同一用户相邻提交的时间间隔估实际耗时（间隔 ≤ 120 分钟取真实间隔，否则首提交记 30 分钟）。

> **口径提示**：第 1 步会把 §6 的 V2 融合工时引入 V1 口径，故仓库/项目页"古法提效比"在缺数提交上实为 V2 工时换算；第 2 步只估实际、不估传统，这类提交因传统分钟为 0 而提效比显示 `-`。即 V1 页面的工时是"真实记录 + 派生估算"的混合。

### 12.6 为什么两套口径不可横向比较
1. **数据源不同**：V2 取 needs 表（融合基线 vs 日历/活跃分母）；V1 取 commits/tasks 表（古法估时 vs 实际估时）。
2. **过滤层不同**：V2 经资格判定 + 异常隔离（§8/§9）剔除极端/不合格样本；**V1 聚合不做任何资格/异常/排除过滤**（`db.go:907-933`），被 V2 隔离的极端机器生成提交在 V1 里全额计入，会抬高 V1 仓库级提效比。
3. **量级与展示不同**：V2 是小数（×100 显示），V1 是百分比（直显）；把 V1 的 300 误当 V2 小数喂给 RatioPill 会显示成 30000%。
