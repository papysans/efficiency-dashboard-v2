# 数据格式与字段说明（上环境用）

> 目的：上环境前对齐——主分支(v1)需要喂什么数据、什么格式；当前 feat 分支(v2)在此基础上**增量**了什么；所有字段含义。
> 适用：分支 `feat/efficiency-v2-pipeline`（已含 v1 + v2 全部表，GORM 自动建表）。DB 默认 `costrict_stat`。

---

## 0. 总览：主分支(v1) vs 当前(v2 增量)

| 维度 | 主分支 main（v1 古法） | 当前 feat（v2 增量） |
|---|---|---|
| **输入数据** | conversation + summary + commit + org | 同一套原始来源；commit JSON 增量使用 `files` 字段；**唯一新增独立输入＝anchor 样本库** |
| **导入命令** | `import-conv` / `import-repo` / `import-org` / `efficiency` | 同上 **＋ `efficiency-v2`** |
| **产出表** | tasks, commits, conversations, sessions, user_org, user_productivity, projects*, user_groups | 同上 **＋ 7 张新表**：conversation_events, session_stage_metrics, needs, user_productivity_v2, anchor_set, baseline_coefficients, baseline_fusion_weights |
| **接口** | /dashboard /sessions /tasks /commits /users /repos /orgs /projects /config | 同上 **＋ `/needs` `/needs/:id` `/efficiency`** |
| **提效比口径** | ancient/real（LLM 估 + 时间片段） | calendar 主指标 = (古法日历−实际日历)/实际日历；work 内部口径；三基线(算法/kNN/LLM)融合 |

**结论**：上环境喂数据，v1 和 v2 使用同一套原始来源（第 1 节）。当前 v2 会额外消费 commit JSON 的 `files` 字段来提高 Need 文件聚类质量；唯一额外独立输入是 **anchor 样本库**（第 4 节）。其余 v2 表由已有 conversation/summary/commit/org 自动计算。

## 1. 输入数据格式（上环境必须提供）

数据按目录树放，路径里的日期 = 该记录时间的「年/月/日」。`repo_addr`/`repo_branch` 需 path-safe 化（转小写、非 `[a-z0-9-]` 转 `-`、去首尾、合并连续 `-`）。

### 1.1 `task/summary/YYYY/MM/DD/<task_id>.json` ⚠️ 必需
> ⚠️ **本地 mnt 抽取里曾缺这一层，导致 import-conv 直接报错、用户无法归属。上环境务必带上。** 一个 session 一个文件，携带**用户身份**。

| 字段 | 类型 | 含义 |
|---|---|---|
| task_id | string | session 唯一标识（= 文件名）|
| user_id | string | 用户唯一 ID（**关键**：会话归属到人靠它）|
| user_name | string | 用户名 |
| client_id | string | 客户端设备指纹 hash |
| client_ide / client_version / client_os / client_os_version | string | 客户端信息 |
| caller | string | 调用来源（chat 等）|
| repo_addr / repo_branch | string | 仓库地址 / 分支 |
| work_dir | string | 工作目录绝对路径 |
| start_time | string(ISO8601) | session 开始时间 |

### 1.2 `task/conversation/YYYY/MM/DD/<task_id>.jsonl` 必需
> 每行一条 request 对话（JSONL）。

| 字段 | 类型 | 含义 |
|---|---|---|
| request_id | string | 请求唯一 ID（session 内唯一）|
| sender | string | user / agent |
| prompt_mode / mode / model | string | 提示模式 / 对话模式 / 模型名 |
| start_time / end_time | string(ISO8601) | 请求起止 |
| process_time / process_ttft | number(ms) | 处理总耗时 / 首 token 耗时 |
| upstream_tokens / downstream_tokens | number | 上行/下行 token |
| cost | number | 费用（缺省按模型价目表算）|
| request_content / response_content / user_input | string | 请求/响应/提取的用户输入 |
| diff | string | 本轮产生的代码变更（3 种格式：unified / JSON 数组 / `<<<BEFORE >>>AFTER`）|
| diff_lines | number | 变更行数 |
| error_code / error_reason | number/string | 错误码/原因 |
| repo_addr / repo_branch / work_dir | string | 仓库/分支/工作目录（可与 summary 冗余）|

### 1.3 `repo/<repo>/<branch>/YYYY/MM/DD/<commit_id>.json` 必需
> 一个 commit 一个文件。silica 含硅量靠它的 diff 与对话 diff 做指纹匹配。

| 字段 | 类型 | 含义 |
|---|---|---|
| commit_id | string | Git 提交哈希 |
| commit_time | string(ISO8601) | 提交时间 |
| repo_addr / repo_branch | string | 仓库 / 分支 |
| git_user_name / git_user_email | string | Git 身份 |
| user_id / user_name | string | 系统用户（关联 git 身份）|
| client_id | string | 客户端指纹 |
| work_dir | string | 工作目录 |
| comment | string | commit message（用于 revert 识别）|
| diff_lines | number | 变更行数 |
| diff | string | 代码变更（同 3 种格式）|
| files | string[] | 本次提交涉及的文件路径。v1 不使用；v2 用于 `needs.touched_files` 和 lv4 文件聚类 |

### 1.4 组织映射（DB DSN 或 CSV，二选一）
> `kbcli import-org --from-db <dsn>` 或 `--from-csv org_mapping.csv`。CSV 表头：

```
user_id,user_name,org1,org2,org3,org4,git_user_name,git_user_email
```
org1~org9 为从上到下的组织层级，空串表示该层不存在。

## 2. 数据库表清单（GORM 自动建表，无需手动 DDL）

### 2.1 主分支共有（v1）
| 表 | 用途 | 主键 |
|---|---|---|
| `user_org` | 用户↔组织映射 | user_id |

| `projects` / `project_tasks` / `project_repos` / `project_commits` | 虚拟项目 | — |
| `user_groups` | 用户分组 | group_id |

### 2.2 【v2 增量】7 张新表
| 表 | 用途 | 主键 | 来源 |
|---|---|---|---|
| `conversation_events` | 对话归一化为事件流（think/edit/verify/...）| event_id | 从 conversations 算 |
| `session_stage_metrics` | 每会话三段(思考/执行/验证)时长+特征 | session_id | 从 events 算 |
| `needs` | **需求**维度（提效比报告在这层）| need_id | 按 branch/PR 聚合 |

| `anchor_set` | **kNN 样本库**（METR + 人工标注）| anchor_id | 外部导入 ⚠️ |
| `baseline_coefficients` | 算法基线系数版本 | coef_version | 拟合/默认 |
| `baseline_fusion_weights` | 融合权重 + 团队密度快照 | fusion_weight_id | 拟合/冷启动 |

## 3. 增量产出表关键字段含义

### 3.1 `needs`（提效比核心）
| 字段 | 含义 |
|---|---|
| need_id / boundary_source / boundary_confidence | 需求 ID / 识别层级(lv1_pr/lv2_branch/lv3_issue/lv4_cluster/lv5_orphan) / 边界置信(high/medium/low/very_low) |
| status | active / merged / abandoned |
| primary_user_id / contributor_user_ids | 主贡献者 / 全部参与人 |
| dev_start_ts / dev_end_ts / merge_ts | 开发开始 / 开发完成 / 上线 merge（merge 不进公式）|
| **total_active_work_corrected_min** | ★进公式的「实际工作量」= 会话活跃工时 + 未覆盖代码按古法速率补算 |
| total_calendar_min | 实际开发日历跨度（去长搁置，含吃饭睡觉）|
| total_loc_net / ai_covered_loc / uncovered_loc | 净变更行 / AI 覆盖行 / 裸 commit 行 |
| ai_code_ratio / silica / uncovered_work_ratio | AI 代码占比 / 含硅量 / 裸 commit 工作量占比 |
| baseline_algo_total_work_min | **基线 A**：算法（古法行速率反推+多维修正）|
| baseline_anchor_knn_work_min / _reason | **基线 B**：kNN 相似锚点估值 / 命中原因 |
| baseline_llm_total_work_min / _confidence | **基线 C**：LLM 结构化估值（可关）|
| baseline_fused_work_min / baseline_spread_work_min | 三方融合工作量 / 离散度 |
| baseline_calendar_min | = fused / team_work_density（古法日历跨度）|
| team_work_density_used / team_profile_used | 用到的团队工作密度 / 团队画像 |
| **efficiency_ratio**（主）/ efficiency_band_low/high | 日历提效比 = (baseline_calendar−total_calendar)/total_calendar + 区间 |
| **work_efficiency_ratio**（内部）| = (fused−corrected_work)/corrected_work |
| confidence_level / outlier_flag | 置信(high/medium/low) / 极值标记(只标不 clip)。outlier_flag=撞了 `efficiency_v2.exclusion.scope` 内的异常类别(=隐藏+不计入聚合)；reason 文本仍记录全部撞线类别(诊断) |
| feature_dependency_risk / *_signal | 特征依赖风险 / 各质量信号(silica/ai_code_ratio/uncovered) |

> 提效比读法：0=没提效；+1=古法是 AI 的 2 倍(省一半)；+4=古法 5 倍；负=AI 拖慢(真实信号，不截断)。

### 3.2 `user_productivity_v2`（按用户·周）
| 字段 | 含义 |
|---|---|
| user_id / week_start / need_ids | 用户 / 周一锚点日期 / 该周需求列表 |
| merged/active/abandoned_need_count | 合并/进行中/废弃需求数 |
| actual_calendar_min / baseline_calendar_min / **efficiency_ratio** | 日历口径(先 sum 分子分母再算) |
| actual_active_work_corrected_min / baseline_fused_work_min / **work_efficiency_ratio** | 工作量口径 |
| coverage_high_confidence / _medium / _low_unreported / _abandoned / _active | 覆盖率构成（low+abandoned>阈值→可信度受限）|
| confidence_limited / confidence_reason | 是否受限 + 原因（拼接串）|
| upstream/downstream_tokens / cost / commit_count / commit_diff_lines | 用量、成本、提交量 |

> 聚合规则：只纳入 `status=merged` 且 `boundary_confidence∈{high,medium}` 的需求；先 sum 分子分母再算比值（防单点极值带飞）。

### 3.3 `anchor_set`（kNN 样本库，第 4 节详述）
| 字段 | 含义 |
|---|---|
| anchor_id / source / source_version / anchor_kind | 锚点 ID / 来源 / 版本 / 类型 |
| **without_ai_minutes** | ★kNN 的标签：不用 AI 完成所需分钟数（必须是 without-AI，不能用 with-AI 时间）|
| human_labeled | 是否人工标注（true 更可信）|
| weight | 权重（设计要半衰期 6 月时间衰减，当前未实现）|
| **feature_vector** | 特征向量(jsonb)，与 need 同口径才能匹配（见第 4 节）|
| labels | 元数据(jsonb) |

## 4. 【v2 增量】anchor 样本库——上环境唯一需要额外准备的输入

kNN(基线 B) 靠 `anchor_set`。**没有可用锚点 kNN 就退出、只跑算法 A**。上环境统一使用一张标准表：

### 4.1 统一交付表

| 文件 | 用途 |
|---|---|
| `docs/data/efficiency_v2_anchor_set.csv` | 标准 anchor 样本表，当前 179 条可用样本 |
| `kbcli/scripts/import_efficiency_v2_anchor_set.sql` | 把标准 CSV upsert 到 `anchor_set` |

CSV 字段与 `anchor_set` 表字段一致：`anchor_id,source,source_version,anchor_kind,human_labeled_minutes,without_ai_minutes,human_labeled,weight,feature_vector,labels,valid_from,valid_to`。

当前 CSV 只保留实际可用的 `internal_ainative_2026` 样本：
- `without_ai_minutes` = 端到端传统预估(人天) × 480 × **校准系数 0.499**
- `feature_vector` = `{log_work_min: ln(端到端实际×480+1), ai_code_ratio: 采纳率}`
- `labels.raw_without_ai_min` 保留未校准原始值；`labels.calib=0.499` 记录校准系数。

### 4.2 来源说明

这张标准表由本地加工材料清洗而来：
- `工时估算数据/AI Native项目提效估算表.xlsx`：原始人工标注表。
- `.local/import_ainative_anchors.py`：本地清洗脚本。
- `.local/ainative_anchors.sql`：本地生成的中间 SQL。

这些文件只作为本地追溯来源，不再作为上环境部署依赖。

METR 种子 `.local/metr_anchors.sql` 暂不纳入统一交付表。原因是 METR 的 `feature_vector` 全是零，代码加载时会跳过，不能作为有效 kNN 样本。

### 4.3 特征向量口径（匹配生效的前提）
- need 特征(`BuildEfficiencyV2NeedFeatureVector`)：`{loc, files, turns, think, exec, verify, log_work_min, ai_code_ratio}`。
- kNN 距离按**键交集**算：METR/fixture 锚点匹配 `{loc,files,turns}`；AI-Native 人工锚点匹配 `{log_work_min, ai_code_ratio}`。
- ⚠️ 上环境若要 kNN 真正发挥相似匹配，**需要生产 need 带上和锚点同口径的特征**；当前 benchmark 数据特征薄(files=0、会话时长≈0)，kNN 近似按工作量规模匹配。

## 5. 配置 + 命令

### 5.1 `kbcli-config.yaml` 关键项
```yaml
stat_database: {host, port, user, password, dbname: costrict_stat}
efficiency_mode: new            # legacy/new/both
efficiency_v2:
  team_profile: balanced        # metr_senior/balanced/ai_heavy
  baseline_defaults:
    weight_algo: 0.60           # 算法基线权重；调高会抬高工作量基线
    weight_knn: 0.15            # 样本库基线权重；当前样本偏低，调低可避免拉低工作量提效
    weight_llm: 0.25            # LLM 基线权重；LLM 关闭时自动重归一化
    team_work_density: 0.35     # 工作量→日历换算密度；只影响日历提效，不影响工作量提效
  stage:
    default_edit_duration_seconds: 30     # 无结束时间时，编辑工具调用默认耗时
    default_read_duration_seconds: 10     # 无结束时间时，读文件工具调用默认耗时
    default_command_duration_seconds: 30  # 无结束时间时，命令/测试工具调用默认耗时
    default_other_duration_seconds: 10    # 其他工具调用默认耗时
    default_message_chars_per_minute: 300 # 消息按字符数估时
ai_estimation: {enabled: false} # 基线 C(LLM) 开关；离线设 false，融合自动重归一化
algo_estimation:
  commit_minutes_per_line: 2.0  # 古法每行代码花多少分钟；优先改这个
  # commit_line_per_minutes: 0.5 # 兼容旧字段：古法每分钟多少行
task_dir / repo_dir / analysed_dir / org_csv_file
```

### 5.2 上环境执行顺序
```bash
# 1) 建表自动完成（首次连库 GORM AutoMigrate）
# 2) 种锚点（v2 必需，否则 kNN 不参与）
psql -U postgres -d costrict_stat \
  -f kbcli/scripts/import_efficiency_v2_anchor_set.sql
# 3) 导入 + 计算
kbcli import-conv        # summary+conversation → sessions/conversations + 指纹
kbcli import-repo        # commit → commits + silica
kbcli import-org --from-csv org_mapping.csv
kbcli efficiency         # v1 古法 → user_productivity
kbcli efficiency-v2      # v2 → conversation_events→stage→needs→user_productivity_v2
# 4) 后端读接口（/api/v2/*）
```

## 6. 上环境 checklist
- [ ] **summary/ 这层一定要有**（带 user_id），否则用户归属失败、silica=0。
- [ ] conversation/ 与 commit/ 的 diff 字段非空（silica 靠它）。
- [ ] commit/ 带 `files` 数组（v2 Need 文件聚类靠它；没有也能跑，但主干裸 commit 更容易落到低置信 orphan）。
- [ ] org 映射就绪（DB 或 CSV）。
- [ ] anchor 样本库已从 `docs/data/efficiency_v2_anchor_set.csv` 导入，否则 kNN 退出只剩算法。
- [ ] config 的 efficiency_mode=new、team_work_density、commit_line_per_minutes 按团队设定。
- [ ] 后端 config.yaml 指向同一 `costrict_stat`，端口 9990。
