## 0. 背景

### 0.1 当前问题

现行系统**内部混用了两种口径**，文档要先统一：

| 位置 | 实际公式 | 口径 | 例 |
|---|---|---|---|
| 后端 `core/utils/calc.go:9` `CalcEfficiencyRatio` | `((ancient - real) / real) * 100` | **提升百分比** | ancient = 4h, real = 1h → **300%** |
| 前端 `ProjectDetailV2.vue:526` 展示 | `ancientWorkDays / actualWorkDays` | **效率倍数** | 4x |
| 字段写入 (`cmd_efficiency.go:177`) | 调 `CalcEfficiencyRatio` | 百分比 | 数值常见 200-500 |

**两种口径数学等价**（百分比 = 倍数 × 100 - 100），但展示混乱导致业务方一会看"300%"、一会看"4x"。

`ancient_minutes` 由 LLM 估算（v1/v2/v3 prompt + few-shot anchors），`real_minutes` 由对话时间片段合并得出。

**新系统统一用"提效百分比"口径**：`1 - real/baseline`（含义跟旧的 `(a-r)/r` 等价但表达更直观，且天然 ≤ 100%）。

实际跑出来"非常恐怖"——常见 300%、500%。根本原因有四：

1. **公式形态错**：纯除法分母小时必爆，理论上无上界
2. **基线不可信**：LLM 估的反事实有系统偏差（METR 实测：人 + LLM 对反事实都偏 39 百分点）
3. **单位粒度错**：度量单位是 task（≈ 一段连续对话），trivial 任务被独立放大
4. **测错了对象**：只测编码环节，但 AI 时代成本大头已经迁移到上游（brainstorm/explore/spec），编码反而是廉价部分

### 0.2 研究支撑

| 来源 | 关键发现 |
|---|---|
| METR (2025, 246 任务 RCT) | 开发者主观感觉 AI 帮自己快了 20%，实测**慢了 19%** |
| Thoughtworks | 编码环节快 30%，但端到端 delivery 只快 **8%**；"50% 提效"是 wild overestimation |
| Bain Tech Report 2025 | 团队级提效落在 **10-15%** |
| 阿里灵码 | 提效 = 编码占比 × AI 代码占比，举例 30% × 40% = **12%** |

行业可观测的合理范围是 **8-20%**。任何系统跑出 50%+ 几乎必然是公式错。

## 1. 设计哲学

**不假装反事实可观测。用多个独立估计源三角验证。估计源收敛时报单值，发散时报区间。"不知道"显式说出来。**

这套哲学在度量学（measurement theory）叫 **triangulation**，在科研叫 **multi-method estimation**。比"挑一个最好的基线"更扛打。

实操形态：

```
提效比 = (T_baseline_calendar - T_actual_calendar) / T_actual_calendar    ← 主指标（calendar 维度）

T_baseline_calendar = T_baseline_work_fused / team_work_density

T_baseline_work_fused = weighted_median({T_algo, T_anchor_knn, T_llm})
weight_i = 1 / MAD_i²   (MAD = 在 anchor 集上的历史绝对误差中位数)

team_work_density = 团队历史 work/calendar 平均（默认 0.25，每天 6h 工作）
```

**为什么用 calendar 维度**：符合"一个需求几天能做完"的业务直觉，含吃喝拉撒睡觉。古法 calendar 通过假设古法工作密度 = 团队当前平均密度反推。

**为什么不 clip**：数学上提效比天然下限是 -1（T_actual = 古法的无穷多倍），上限无穷大（古法相对 AI 的倍数即可越高越大）。0 = 没提效，1 = 提效 100%（古法是 AI 的 2 倍时间），10 = 提效 1000%（古法是 AI 的 11 倍时间）。负值（AI 拖死人）是真实信号，**METR 已证实存在**，截断等于撒谎。极端值通过 `outlier_flag` 暴露，业务方默认看聚合数字。

**报告三件套**：`ratio`（点估计）、`band`（不确定度区间）、`confidence`（high/medium/low）。

## 2. 度量单位

### 2.1 双层模型

| 层 | 角色 | 主键 |
|---|---|---|
| **Need**（需求） | 度量单位，提效比报告在这一层 | `repo:branch` |
| **Session**（会话） | 数据采集的原子单位（不是度量单位） | `session_id` |

**关系**：

```
Need (聚合层)
  ├── Session A (采集层) → 特征 + 三段时间
  ├── Session B (采集层) → 特征 + 三段时间
  └── Commits + PRs        → 复杂度 + 结果质量
```

### 2.2 为什么不用 Session 作为度量单位

实际工作中一个需求经常横跨多个 session（user 实测）。Session 作为度量单位会把"一个需求"切成碎片，违反业务直觉。

### 2.3 Need 边界识别

**主键 = git branch**。

理想情况是 "一个 feature 分支 = 一个 Need"。但**现实里开发者不一定老实开分支**——有人直接 commit 到 main、有人一个长期分支做 N 个需求、有人 squash merge 后历史消失。**只靠 branch 一种信号识别 Need，识别率最多 60-70%**。剩下的要靠 fallback 链。

#### 2.3.1 多信号 fallback 链

按优先级试，第一个能识别的赢：

```
Lv1: PR 维度        一个 PR = 一个 Need
                    要求：commits 关联到一个明确 PR
                    
Lv2: branch         git branch（过滤 main/master/develop/release-*）
                    要求：commits 在非主干 branch 上
                    
Lv3: issue 关联     从 commit message 解析 #1234 / JIRA-123 / [TASK-xxx]
                    要求：commit message 含 issue 标识符
                    
Lv4: 文件聚类       同 author + 7 天滑窗 + 文件 Jaccard 相似度 > 0.5
                    把相关 commits/sessions 聚成一组
                    
Lv5: 兜底           need_id = "orphan-{user_id}-{week}"
                    完全无法归类的活动，按"周"打包
```

#### 2.3.2 每条 Need 标记识别置信度

| Fallback 层级 | `boundary_confidence` 值 |
|---|---|
| Lv1 PR 维度 | high |
| Lv2 branch | high |
| Lv3 issue 关联 | medium |
| Lv4 文件聚类 | low |
| Lv5 orphan 兜底 | very_low |

#### 2.3.3 低置信度的处理

- **`boundary_confidence ∈ {low, very_low}` 的 Need 不进团队聚合报告**（防止污染）
- 仪表盘单独有"未归类活动"维度，让管理者能看到这部分工作量但不参与提效比统计
- 这类 Need 在样本库构建时也不作为 anchor 候选

#### 2.3.4 长期 branch 切分

不论用哪个 fallback 识别出的 Need，**跨度超过 30 天自动 split 成 sub-need**（按周或按 commit 间隔）。

#### 2.3.5 时间字段拆分（开发时间 vs 上线时间）

原设计 `end_ts = merge 时间 或 最后 session 结束` 是错的。等 reviewer merge 的时间不该污染"开发周期"。

修正：

```
dev_start_ts          第一个 session 开始
dev_end_ts            最后一个 session / commit 结束  ← "开发完成"
merge_ts              实际 merge 时间（可空）         ← "上线"
wait_for_review_min   merge_ts - dev_end_ts          ← 协作信号，不进公式
```

#### 2.3.6 三类"实际时间"：person-min / wall / calendar（公式概念区分）

**关键概念区分**：baseline 是 person-hours（METR 每个任务都是单人完成的人力工作量）。提效比公式分子必须也是 person-time，不能用 wall-clock，否则多人协作会被算成"超高提效"（两人各干 1h，wall = 1h，baseline = 2 person-h，比值 0.5 → 假提效 50%）。

```
T_actual_work_person_min   ★ 进提效比公式
                           = Σ 每个 contributor 每个 session 的 active min
                             不去重重叠，这是 person-minutes
                           例：两人各 active 60min → 总 120 person-min
                           
T_actual_wall_min          display 用，不进公式
                           = 各 session 时间区间的并集
                             去重重叠，这是 wall-clock
                           例：两人各 active 60min 同时段 → 并集 60min
                           
T_actual_calendar_min      display 用，不进公式
                           = wall_clock(dev_start → dev_end)
                             - Σ(gap_i for gap_i > idle_threshold)
                           含义：开发跨度信号，含吃饭睡觉，剔除长搁置
                           ⚠️ 跟 baseline 概念不对齐，禁止直接对比
                    
idle_threshold             默认 3 天，admin 可配置
                           gap ≤ 3 天 → 全算入（含周末/睡觉）
                           gap > 3 天 → 视为搁置，剪掉
```

**单人 Need**：person_min ≈ wall_min，两者无差异。
**多人 Need**：必须用 person_min 进公式，wall_min 仅作为协作信号展示。

#### 2.3.6b 非 AI 人工工作的漏算修正

**问题**：如果开发者大部分时间在 IDE 手写代码、查资料、开会、Slack 沟通，最后 commit 进来。AI session 只占总工作量的小部分。

- `T_actual_work_person_min` 只来自 Claude session active → 偏低
- `T_baseline_work` 按 commit 总 LOC 反推 → 偏高
- 提效比虚高（假帮人 100%）

**修正方案**（复用 silica 的 nonAiMinutes 思想）：

#### 裸 commit 判定（窗口必须收窄，不能用宽松"前后 session 之间"）

```
配置参数：
  pre_margin_min  = 30  默认（admin 可调）
  post_margin_min = 60  默认（admin 可调）

对每个 Need 的每个 commit：
  
  session_window 关联条件（任一满足即"session 关联"）：
    (a) commit.ts 落在某个 contributor 的某个 session 的
        [session.start - pre_margin, session.end + post_margin] 内
    (b) commit 修改的文件集合与该 session 编辑过的文件集合有交集
        （文件级匹配，防止误判同时间段无关 session）

  不满足 → "裸 commit"（uncovered）

⚠️ 不能用"前一个 session 结束到后一个 session 开始之间"
   那样窗口太宽，早 session + 下午手写 commit + 晚 session 会被误判
```

#### 三个信号字段（不要混用）

```
1. ai_code_ratio        = ai_covered_loc / 总 LOC
                          含义：AI 代码占比（含硅量覆盖率）
                          用途：AI 参与度信号
                          
2. uncovered_loc        = Σ commit.totalLines  WHERE commit 是裸 commit
                          含义：完全脱离 session 的人工 commit LOC
                          用途：进入 estimate_uncovered_human_time 反推
                          
3. uncovered_work_ratio = estimate_uncovered_human_min / total_active_work_corrected_min
                          含义：人工裸 commit 工作量占总工作量比例
                          用途：置信度判断（裸 commit 多 → AI 提效信号弱）
```

#### 工作时间汇总

```
T_actual_work_corrected = T_session_active_person_min
                        + estimate_uncovered_human_time(uncovered_loc)

estimate_uncovered_human_time(uncovered_loc):
  调 estimateCommitAncientMinutes(uncovered_loc)
  含义："承认这块裸 commit AI 没帮，按古法速率算 actual 投入"
```

#### 避免双算（关键）

| 场景 | 处理 |
|---|---|
| session 时间窗口内（含 margin）手写、被 silica 匹配 | session active 已覆盖，不重复计 |
| session 时间窗口内手写、silica 没匹配（指纹漏） | session active 已覆盖，不重复计 |
| **commit 文件与 session 文件有交集** | 视为 session 关联，**不重复计** |
| **完全脱离 session 的裸 commit** | session active 没覆盖，**走 uncovered 反推** |

#### 置信度联动（用对应信号）

```
ai_code_ratio_signal:
  if ai_code_ratio < 0.3:
      → "AI 代码占比低，AI 参与度信号弱"
      → 置信度降级

uncovered_work_ratio_signal:
  if uncovered_work_ratio > 0.3:
      → "裸 commit 工作量占比高，AI 提效信号弱"
      → 置信度降级
```

**两个信号独立**：AI 代码占比低 ≠ 裸 commit 多。前者是"session 内人工写得多"，后者是"session 之外的工作多"。

进入提效比公式的实际工作时间字段就是 `T_actual_work_corrected`（不是裸的 `person_min`）。

#### 2.3.7 提效比公式（calendar 维度为主指标，含吃喝拉撒）

**业务直觉**：日常说"这个需求 3 天能做完"是含睡眠/吃饭/周末的 calendar 概念，不是"只算敲键盘的时间"。我们的主指标也按这个尺度算。

```
提效比 (主指标) = (T_baseline_calendar - T_actual_calendar) / T_actual_calendar

其中：
  T_actual_calendar    = dev_end_ts - dev_start_ts - 长搁置（§2.3.6）
                         单位 calendar 小时（含睡眠/吃饭/周末）
                         
  T_baseline_calendar  = T_baseline_work / team_work_density
                         按"团队工作密度"反推古法 calendar 跨度
                         
  T_baseline_work      = 三方法融合的古法工作时间（§4 详述）
  
  team_work_density    = 团队历史平均工作密度（每天工作小时数 / 24h）
                         默认 0.25（约 6h/天，行业经验值）
                         从团队 merged Need 数据每周拟合更新

读法：
  提效比 = 0     表示 古法 = AI，没提效
  提效比 = 1     表示 古法 = 2 × AI，提效 100%（AI 用了一半时间）
  提效比 = 4     表示 古法 = 5 × AI，提效 400%（AI 用了 1/5 时间）
  提效比 = -0.5  表示 古法 = 0.5 × AI，反向（AI 反而花了 2 倍时间）
```

**为什么不直接用 work 公式**：

之前一版试过 `提效比 = 1 - work_ratio`，但跟"一个需求几天能做完"的日常直觉脱节。新版本主指标用 calendar，符合业务方对"开发时间"的理解。

**为什么从 `1 - actual/baseline` 改成 `(baseline - actual)/actual`**：

旧形式上限被锁在 100%（即使 AI 把 1 天的活压到 1 小时也只能显示"提效 95.8%"），无法表达"AI 把古法 10 天活压到 1 天 = 提效 9 倍"这种大幅提效。新形式上限无穷，更贴合"AI 把活儿压扁了多少倍"的业务直觉。下限不变（-1），表示"AI 至少让你花了 ∞ 倍时间"在数学上等价于"古法 = 0"。

#### 2.3.8 team_work_density 怎么算

**核心假设**：古法做同一需求，开发者吃饭睡觉的时间比例不会因为有没有 AI 而改变——古法时代他也是每天工作 6h，剩下 18h 干别的。

```
team_work_density = Σ(所有 merged 高置信度 Need 的 T_actual_work_corrected)
                  ─────────────────────────────────────────────────────────
                    Σ(所有 merged 高置信度 Need 的 T_actual_calendar)

例：团队过去 6 个月完成 50 个 Need
    总工作时间 500h ÷ 总 calendar 跨度 2000h = 0.25
    → team_work_density = 0.25（每天工作约 6h）
```

**约束**：

- 冷启动期数据稀疏 → 默认 0.25（行业经验值）
- 后台每周重算一次
- 持久化到 `baseline_fusion_weights` 表（含历史快照）

#### 2.3.9 work 提效作为内部下钻字段

```
work 提效 (内部参考) = (T_baseline_work - T_actual_work_corrected) / T_actual_work_corrected
                     ↑
                     这个数字对业务方不暴露，仅供算法工程师下钻调试
```

**为什么两个数字会不一样**：

```
calendar 提效 = (T_baseline_calendar - T_actual_calendar) / T_actual_calendar
              = (T_baseline_work / team_density - T_actual_calendar) / T_actual_calendar
              
work 提效     = (T_baseline_work - T_actual_work) / T_actual_work

两者差异 ∝ actual 这个 Need 的工作密度偏离团队平均的程度
```

- 如果 actual 工作密度 = 团队平均 → 两个数字相等
- 如果 actual 跨夜了（工作密度低于团队平均）→ calendar 提效 < work 提效（跨夜的代价）
- 如果 actual 紧凑做（工作密度高于团队平均）→ calendar 提效 > work 提效

**这是好的特性**：calendar 提效真实反映"你这个 case 工作节奏对交付速度的影响"。

#### 2.3.10 公式不做 clip

无论 calendar 还是 work 维度，**都不做 clip**。

- 上限：无穷大（古法相对 AI 的倍数越大、提效越高，比值理论无界）
- 下限：-1（即 actual → ∞，等价于古法 = 0；实际不会出现）
- 0 = 没提效；正值 = 提效；负值 = AI 拖死人（METR 已证实存在）
- 极端值通过 `outlier_flag` 标记
- 业务方看聚合数字（先 sum 分子分母再算）
- 单条 Need 数字落在极端区间，UI 层标红但**数据层忠实算法输出**

#### 2.3.11 仪表盘输出字段

```
主指标：
  提效比                  = (T_baseline_calendar - T_actual_calendar) / T_actual_calendar
  
时间对比（业务方直观看）：
  实际开发跨度（含休息）  = T_actual_calendar          例 25h ≈ 1.04 天
  古法估算跨度（含休息）  = T_baseline_calendar        例 88h ≈ 3.7 天
  ✅ 这两个可以直接对比（用同样的"含休息"尺度）
  
内部下钻字段（业务方默认不显示）：
  T_actual_work           严格活跃工作时间
  T_baseline_work         三方融合古法工作时间
  team_work_density       用到的团队密度
  work 提效               (baseline_work - actual_work) / actual_work
```

## 3. Session 内三段切分

### 3.1 切分规则（纯工具调用流，按事件类型逐条归属）

之前用"第一次 Edit / 最后一次 Edit"切大段，把 edit→test→edit 循环里的 test 全归到执行段，**严重低估验证段**。改成**按事件类型逐条归属**。

#### 3.1.1 工具事件分类

```
EDIT_TOOLS（代码修改） = {
  Edit, Write, NotebookEdit, MultiEdit, ApplyPatch,
  Bash 类型为 "git apply" / "git am" / "patch -p" 等
  外部导入流程产生的修改（通过 sidecar 标记）
}

VERIFY_TOOLS（验证活动） = {
  Bash 命令白名单匹配以下模式之一：
    test:        "go test", "npm test", "pytest", "jest", "cargo test", "mvn test", ...
    build:       "go build", "npm run build", "make build", "cargo build", "mvn package", ...
    typecheck:   "tsc", "mypy", "go vet", "cargo check"
    lint:        "eslint", "golangci-lint", "ruff", "rubocop", "pylint", "rustfmt --check"
    check:       "...check..." 命令
  
  Read（在"验证期"内的 Read 视为代码审阅）
  Grep（同上）
}

OTHER_BASH = Bash 不在 VERIFY 白名单内的所有命令
  例如：迁移脚本、代码生成器、数据导入、部署脚本、`run` 类的"跑服务"
  归 OTHER 桶，进入 active 总量计算
  ⚠️ 但不进入三段（思考/执行/验证）任一段的 active_min 计算
  V1 这样保守处理；V2 可加用户配置白名单

THINK_ACTIVITIES = {
  纯对话消息（user / assistant text 无 tool_use）
  Read / Grep（在"思考期"内）
  WebFetch / WebSearch
  ExitPlanMode 事件
  TodoWrite
}
```

**工具事件标准化**：所有"改了代码的行为"必须归一化为 EDIT 事件，否则切分失真。V1 至少覆盖 Edit/Write/NotebookEdit/MultiEdit + 显式 patch shell；外部 CI bot、自动化 lint 修复打 `source = external_bot` 跳过。

#### 3.1.2 切分规则：按 Edit 事件序列分循环

```
状态机：
  初始 state = THINK（思考期）
  
  扫描 session 事件序列：
    遇到第一个 EDIT_TOOLS 事件：
      state ← EXEC（首次进入执行）
      之前所有事件归 THINK
    
    在 EXEC 状态下：
      EDIT_TOOLS 事件本身 → 执行段
      EDIT_TOOLS 后到下一个 EDIT_TOOLS 之前的 VERIFY_TOOLS → 验证段
      （即使在"执行期"内，test/build 也算验证）
    
    最后一个 EDIT_TOOLS 之后的所有事件 → 验证段（终极验证）
```

**直观例子**：

```
session 事件序列：
  [10:00] user msg "我要加 forgot password 功能"
  [10:03] Read auth.go
  [10:08] Edit auth.go                ← 第一次 Edit，进入 EXEC
  [10:12] Bash "go test ./..."        ← 归验证段
  [10:14] Edit auth.go                ← 修 bug，归执行段
  [10:16] Bash "go test ./..."        ← 归验证段
  [10:18] Edit reset_pwd.go           ← 归执行段
  [10:30] Bash "go test ./..." pass   ← 归验证段（终极验证）
  [10:32] user msg "看起来 ok"

切分结果：
  思考段 = [10:00, 10:08)  = 8min
  执行段 = Edit 事件本身的时间累计 = 几次 Edit 操作之和
  验证段 = 各 Bash test 时间 + 最后阶段
```

#### 3.1.3 工具事件的 duration 定义（关键，否则执行段会被压成 0）

Edit / Bash / Read 这类工具调用如果只记一个时间戳没有 end，stage_active_min 会被严重低估（特别是执行段，因为 Edit 事件密集但点状）。

**duration 推算顺序**：

```
对每个事件 e：
  duration(e) =
    priority 1: 如果 e 有 end_ts → end_ts - start_ts
    priority 2: 如果 e 无 end_ts，但下一个事件 e_next 在同 session 且时间间隔 ≤ 5min
                → duration = e_next.start_ts - e.start_ts
    priority 3: 否则 → 默认最小持续时间（Edit/Write = 30s，Bash = 由命令类型推估，
                Read/Grep = 10s，对话消息 = 字符数/300）
```

#### 3.1.4 stage active time 计算

```
think_active_min  = gap-merged sum(duration(events tagged as THINK))
exec_active_min   = gap-merged sum(duration(events tagged as EXEC))
verify_active_min = gap-merged sum(duration(events tagged as VERIFY))
other_active_min  = gap-merged sum(duration(events tagged as OTHER))
                    ↑ 不进三段，但进 active 总量
```

每段独立做 gap-merge（5min 阈值）。

⚠️ **旧版本的"按时间段切分"已废弃**。不要再按 `[session_start, first_edit) / [first_edit, last_edit] / (last_edit, session_end]` 切——那会把 edit→test→edit 循环里的所有 test 全归执行段，严重低估验证段。**只用上面 §3.1.2 的事件状态机**。

### 3.3 active time 计算

复用现有 `calcTaskRealMinutes` gap-merge 逻辑，独立应用到每个 stage：

```
对 stage 内所有 message + tool_use 时间戳排序
相邻间隔 ≤ gap_threshold (默认 5min) → 合并到当前片段
超过 → 结束片段，加 extension_min (默认 2min)，开新片段
stage_active_min = Σ 各片段时长
```

Need 级 active 分两类：

```
Need_active_person_min  ★ 进提效比公式
                        = Σ(每个 contributor 每个 session 每段 active)
                        不去重重叠，per-contributor sum
                        
Need_active_wall_min    display 用，不进公式
                        = 各 session 时间区间并集（去重重叠）
                        反映"项目占用的墙钟时长"
```

**单人 Need**：person 和 wall 相等。
**多人协作 Need**：必须用 person 维度进公式（基线是 person-hours）；wall 仅作协作信号。

### 3.4 边界情况

| Case | 处理 |
|---|---|
| Session 无任何 Edit/Write | 整段 = 思考；exec/verify active = 0 |
| 只有 1 次 Edit/Write | exec 是单点；verify = 之后所有 |
| 第一条消息就是 Edit | think active = 0；如果跨 session 关联同 Need，把前 session thinking 算入同 Need |
| Session 结束时还在 Edit（compaction 截断） | verify active = 0；不强行加 phantom 时间 |
| Edit + 之后只有失败 Bash → 中止 | verify = 0；标记 `incomplete = true` |
| 同 Need 多 session 时间重叠（多人协作） | **公式分子用 person-min sum（不去重）**；wall 字段用区间并集（display 用） |
| Need 内有"裸 commit"（无 session 关联） | uncovered_loc（§2.3.6b 窗口收窄判定）反推加到 actual；uncovered_work_ratio > 0.3 时降级置信度 |

### 3.5 已知局限（不在 V1 内解决）

| 局限 | 后果 | 计划 |
|---|---|---|
| **跨 session 验证**：最后一次 Edit 之后的验证活动可能跨 session 边界，被归到下个 session | 验证成本可能被分摊到下个 session | V1 接受；记入 incomplete 标记 |
| **工具事件不完整**：CI bot 自动修复、外部 lint 工具改动等可能漏 | exec 段虚高 | V1 用 `source = external_bot` 显式跳过；V2 标准化所有来源 |
| **Bash 类型识别启发式**：判定 Bash 是 test/build 还是别的事，依赖命令字符串匹配，可能误判 | 极端情况 verify_active_min 估算偏差 | V1 用启发式；V2 加 user-config 命中模式 |

## 4. 三个独立基线

### 4.1 关键概念：AI-uplift vs peer-relative

| 训练数据来源 | 基线代表 | 等价于回答 |
|---|---|---|
| pre-AI 数据 (PROMISE) / AI-无 AI 配对 (METR) | **AI-uplift 反事实** | "不用 AI 该花多久" |
| 你自己团队的 AI-assisted 历史数据 | peer-relative 基准 | "你和团队平均比快慢" |

**只有第一种叫"提效比"**。所有基线的训练数据**必须含 pre-AI 或配对成分**，否则得到的是 peer-relative 不是 AI-uplift。

### 4.2 Baseline A：混合估算（思考/验证 经验估算 + 执行 反推）

#### 4.2.1 两类本质：经验估算 vs 反推

| 段 | 有没有"硬产出" | 估算方式的本质 |
|---|---|---|
| **思考段** | 无（产出是脑子里的方案） | **经验估算**：过程信号（读文件数/对话轮数/输入字符数）× 历史单价 |
| **执行段** | **有**（diff、commit、files、complexity、含硅量） | **反推**：硬产出 × 已校准单价直接算 |
| **验证段** | 无（产出是"代码 ok"结论） | **经验估算**：test 跑了几次、re-edit 几次 |

**关键差异**：经验估算中间隔了一层"猜"，反推直接套用。**反推相对其他两段更直接**——但**不是"最可信"**，依然有污染源（见 §4.2.5）。

#### 4.2.2 思考段（经验估算）

```
T_A_think(s)  = α_t · think_user_chars
              + β_t · think_files_read
              + γ_t · think_turns
              + δ_t · think_plan_mode_used
```

#### 4.2.3 执行段（反推：复用现有 silica + algo_estimator）

**核心机制：复用现有"含硅量（silica）系统"**

`silica.go::calcCommitDerivedMinutes` 已经做了精确归属：

```
对每个 commit：
  totalSilica = AI 生成代码行数 / 总代码行数
  aiMinutes    = 匹配到的 task.TaskRealMinutes 累加（AI 部分耗时）
  ancientLines = totalLines × (1 - totalSilica)
  nonAiMinutes = estimateCommitAncientMinutes(ancientLines)
  realMinutes  = aiMinutes + nonAiMinutes
```

含硅量精确到每一行代码的指纹（hash 匹配），比 token 比例精细得多。

**方法 A 的执行段反推就是把这套用反过来**——不分 AI/人写，假设全部由人手写：

```
T_A_exec(need) 反推公式：

Step 0: 过滤污染源 ⚠️ 重要
        从 totalLines 里剔除：
          · lock 文件（package-lock.json / yarn.lock / go.sum 等）
          · generated code（标注 generated 的文件、proto 输出等）
          · formatter-only changes（仅空白/缩进变化）
          · 大段连续删除（> 200 连续删除行 → 标 review，不全部计入）

Step 1: 对每个 commit，调用 estimateCommitAncientMinutes(totalLines_filtered)
        → 得到"假设全部人手写"的工作时间（古法执行段基线）

Step 2: 叠加新维度修正
        + Σ files_edited × file_coordination_min       (多文件协调成本)
        + Σ complexity_delta × complexity_factor       (复杂度修正)
        + Σ re_edit_count × iteration_penalty          (迭代成本)

Step 3: 含硅量交叉验证
        如果 totalSilica 极低（AI 没写多少）但 T_A_exec 估的远大于 T_actual
        → flag warning，说明这段执行可能不是 AI 协助下完成的
```

#### 4.2.3.5 与现有 commit_ancient_minutes 的关系（明确替代）

现有 `commits.commit_ancient_minutes` 字段由 `silica.go:598` 调 `estimateCommitAncientMinutes(len(fpHashes))` 写入。

**新系统的 `baseline_algo_exec` 完全替代这条计算**，不在旧值上叠加：

| 系统 | 字段 | 计算 |
|---|---|---|
| 旧路径（legacy 双轨） | `commits.commit_ancient_minutes` | 旧逻辑保留，继续写 |
| 新路径（v2） | `needs.baseline_algo_min` 中执行段部分 | **重新计算**，含过滤 + 多维修正 |

两套对同一 commit 算出的 ancient 通常会不同——这是预期的，可以用作对比研究。**严禁**在新系统里读取旧的 `commit_ancient_minutes` 字段做累加，那是双算。

**用伪代码表示**：

```go
func computeBaselineAExec(need *Need) float64 {
    var total float64
    for _, commit := range need.Commits {
        // 复用现有 algo_estimator.go 的核心反推
        coreEstimate, _ := estimateCommitAncientMinutes(commit.TotalLines)
        
        // 新增维度修正
        fileCoord     := float64(commit.FilesEdited) * cfg.FileCoordMin
        complexityAdj := commit.ComplexityDelta * cfg.ComplexityFactor
        reEditPenalty := float64(commit.ReEditCount) * cfg.IterationPenalty
        
        total += coreEstimate + fileCoord + complexityAdj + reEditPenalty
    }
    return total
}
```

#### 4.2.4 验证段（经验估算）

```
T_A_verify(s) = α_v · verify_bash_test_count
              + β_v · verify_re_edits
              + γ_v · verify_turns
```

#### 4.2.5 含硅量作为执行段的可信度信号

含硅量本身就是"AI 帮了多少"的精确测量，可以反过来用作 sanity check：

```
expected_silica_lower_bound = 0.3   (config)

if need.totalSilica < expected_silica_lower_bound:
    # AI 在这个 need 里写的代码很少
    # 即使提效比算得很高，也不应该全归功 AI
    boundary_confidence ← min(boundary_confidence, "low")
    reason 添加："silica 过低，AI 协助度存疑"
```

#### 4.2.6 系数来源（关键：必须从古法数据拟合）

**严重警告**：现有 `cfg.AlgoEstimation.CommitLinePerMinutes = 1.0` 是为 AI 时代的"AI-assisted 估算"调过的，**不能直接当成"古法系数"用**！否则 baseline 会严重低估（例如 120 LOC 算成 2h 古法时间，实际古法可能要 10-15h）。

**核心反推系数（执行段）的来源**：

| 系数 | AI 时代值（旧） | 古法值（V1 拟合） | 数据源 |
|---|---|---|---|
| `lines_per_min`（古法 LOC/min 速率） | 1.0 | **约 0.2**（5x 慢于 AI 时代） | METR 246 任务 without-AI 时间 / LOC |
| `file_coordination_min` | 0 | 30min/文件 | METR + PROMISE 拟合 |
| `complexity_factor` | 0 | 30min/cyclomatic Δ | METR 拟合 |
| `iteration_penalty` | 0 | 20min/迭代次数 | METR 拟合 |

**新系统必须用拟合后的古法系数**，不能直接读 `cfg.AlgoEstimation.CommitLinePerMinutes`。旧字段保留给 legacy 路径用。

**经验估算系数（思考/验证段）**：

```
冷启动：
  METR 246 个配对任务拟合 → AI-uplift coefficients
  PROMISE Desharnais 做 sanity check
  存到 baseline_coefficients 表 version=v0

运行时：
  每周后台 Bayesian update（见 4.5）
  用最新版本系数计算
```

**Profile 配置（admin 可调，应对不同团队风格）**：

```
team_profile:
  · "metr_senior"   METR 资深开发者基线（小需求 AI 提效 ~ 0%）
  · "balanced"      平衡先验，行业平均（小需求 AI 提效 ~ 30-50%）
  · "ai_heavy"      AI 重度依赖团队（小需求 AI 提效 ~ 50-80%）

冷启动默认 "balanced"，admin 可根据团队反馈切换
积累 30+ anchor 后自动 calibrate
```

#### 4.2.7 T_A 整体汇总

```
T_A(session)  = T_A_think + T_A_exec + T_A_verify
T_A(need)     = Σ T_A(session)
```

副产品：**置信度可以分段算**。执行段占比大的 Need → 整体可信度高；思考段占比大的 Need → 整体可信度低。

### 4.3 Baseline B：Anchor-KNN（纯算法，非参数）

**结构**：

```
feature_vector(need) = [
    log(total_loc_net + 1),
    log(total_files_touched + 1),
    log(total_user_chars + 1),
    log(total_turns + 1),
    complexity_delta,
    ai_token_ratio,
    ...
]

对新 Need v：
  distances = [euclidean(v, a.feature_vec) for a in anchors]
  top_k = K 个距离最小的 anchor
  weights = [1 / (d + ε) for d in top_k_distances]
  T_B(need) = Σ(w_i · anchor_i.human_labeled_minutes) / Σ w_i
```

**Anchor 库**：

```
v0:  METR 246 个任务 → feature_vec + without_AI_actual_minutes
v1+: 加你团队人工标注的少量 anchor（10-50 个覆盖你的 domain）
```

K 推荐 5-10。anchor 数 < 30 时退化为全表加权平均。

**注意**：anchor 必须是 **without-AI 时间**（METR 字段里有），不能用 with-AI 时间，否则退化为 peer-relative。

### 4.4 Baseline C：LLM 结构化估算（成本受控版）

**原设计的问题**：直接把会话原文（甚至截断版）丢给 LLM 估，长 session 截断丢信息、每 session 调一次成本随会话数线性涨、prompt 非结构化模型用不上的信号多。

**改造为三件事**：

#### 4.4.1 LLM 不看原始会话，只看结构化摘要

prompt 输入从"截断对话原文"换成固定模板：

```
【需求摘要】
分支：feature/forgot-password
跨会话数：3
总活跃时间：5h（思考 41% / 执行 47% / 验证 12%）
产出：+120 / -15 LOC，4 文件
文件类型：3 个 .go / 1 个 .ts
工具调用：Read 12 / Grep 18 / Edit 8 / Bash 7
关键决策（来自 ExitPlanMode / TodoWrite）：
  · 决定方案 B（直接邮件发链接，不做短信验证）
  · 拆 4 个 task

【每会话一句话摘要】（每段 ≤ 50 字）
  会话1: 调研登录页结构，确定方案 B
  会话2: 实现主流程（4 文件）
  会话3: 修 2 个测试用例

【few-shot 锚点：METR 配对任务的"不用 AI 时间"】
  ...

【请估】
一位中级开发者不用 AI 完成此需求的分钟数。
输出 JSON: {think_min, exec_min, verify_min, total_min, confidence}
```

**输入约 1500 token，输出约 200 token**。单次成本约 ¥0.005。

#### 4.4.2 Need 维度一次调用，不是 session 维度

- 旧设计：每 session 调一次，sum 到 Need → 成本随会话数线性涨
- 新设计：**Need 维度一次调用**，让 LLM 直接估整个需求 → 成本与会话数无关

```
T_C(need) = LLM_estimate_v4(need_structured_summary, METR_anchors)
```

#### 4.4.3 会话一句话摘要怎么来

| 方式 | 成本 | 准度 | 用法 |
|---|---|---|---|
| **模板规则** | 0 | 糙（取首条 user 消息前 50 字 + 文件统计） | 兜底 |
| **小模型摘要** | 极低（Haiku 级别） | 高 | 推荐 |

**推荐小模型**：每会话结束后跑一次 Haiku 摘要，存到 `session_stage_metrics.summary` 字段。摘要是离线动作，**对提效比计算的关键路径无影响**。

#### 4.4.4 输出结构化（与方法 A 对齐）

LLM 输出从单值 `total_min` 变成 `{think_min, exec_min, verify_min}`——**和方法 A 一样按 stage 估**，融合时可以按 stage 维度分别融合，颗粒度更细。

#### 4.4.5 与现有 `callAIForAncientEstimationV3` 的关系

- **旧 LLM 估算系统（legacy）**：仍调用 V3，按 task 维度直接喂截断对话。**保留不动。**
- **新系统 Baseline C**：调用新函数 `callAIForNeedEstimationV4`，使用结构化摘要 + Need 维度。
- 两套互不影响。后续如果想升级，可以同步演进，但 V1 不强求。

**为什么保留**：作为第三个独立信号源，融合时增加鲁棒性。即使不准也不浪费——偏差会被融合权重自动降权。

### 4.5 Bayesian Coefficient Update

**核心问题**：每天积累的内部数据都是 AI-assisted，怎么"修正" A 而不污染 A 的 AI-uplift 性质？

**做法**：

```
α_new = (precision_prior · α_prior + precision_data · α_data_estimate)
        / (precision_prior + precision_data)

precision_prior = 1 / σ²_prior      (METR 拟合给出的方差)
precision_data  = 1 / σ²_data_obs   (内部回归给出的方差)
```

**关键约束**：

- `σ²_prior` 取较小值（强先验）→ 内部数据要"非常一致地反对"先验才能撬动
- 这样防止"团队普遍用 AI" 的事实把 α 拉向 peer-relative
- 可手工锁定某些系数为先验值（exec 系数最敏感，建议锁）

数学上是 **Bayesian linear regression with informative prior**，标准方法。

### 4.6 融合：inverse-variance weighting

对每个 anchor，计算每基线预测误差：

```
e_X(a) = |T_X(a) - human_labeled(a)|    for X ∈ {A, B, C}

MAD_X = median({e_X(a) for a in all anchors})
weight_X = 1 / MAD_X²
```

每周后台跑一次。融合：

```
T_fused(need) = (w_A · T_A + w_B · T_B + w_C · T_C) / (w_A + w_B + w_C)
```

历史表现差的基线自动降权。**不需要人拍板"信谁"，数据决定。**

#### ⚠️ 独立性的重要 caveat

三方对照的前提是**三个估算源相互独立**。实际上 A/B/C 都大量依赖共同特征：

| 方法 | 主要特征 |
|---|---|
| A 参数模型 | LOC、files、turns、complexity |
| B Anchor-KNN | LOC、files、turns（同一个 feature_vector）|
| C LLM 估算 | 结构化摘要里也是 LOC、files、阶段时间 |

**共同特征偏差三方都会一起偏**。典型场景：

- AI 生成的代码 LOC 偏高（boilerplate / 重复模式）→ 三个方法都会给出偏高的"古法时间"
- 三方一致 ≠ 一定准；可能是"一起错"

**唯一真正独立的对照**是人工 anchor 标注。所以：

- ComparisonLogger 必须每周跑一次三方 vs 人工 anchor 的偏差对比
- 当三方一致但跟人工偏差大时，**降低整体置信度**（不是降低 spread 信号的置信度）
- 长期看，人工 anchor 是这套系统的"真值锚"，规模必须持续扩大

### 4.7 不确定度 + 最终公式

**注意**：`T_A`、`T_B`、`T_C` 都是工作时间（work），三方法各自的输出。融合后转 calendar 算主指标。

```
Step 1: 三方法融合（工作时间维度）
  T_baseline_work_fused = (w_A · T_A + w_B · T_B + w_C · T_C) / (w_A + w_B + w_C)
  T_spread_work         = std({T_A, T_B, T_C})

Step 2: work → calendar 转换（按团队密度）
  T_baseline_calendar      = T_baseline_work_fused / team_work_density
  T_baseline_calendar_low  = (T_baseline_work_fused + T_spread_work) / team_work_density
  T_baseline_calendar_high = (T_baseline_work_fused - T_spread_work) / team_work_density
  
  team_work_density 来自 baseline_fusion_weights 表最新快照
  默认 0.25（冷启动 + 数据不足时）

Step 3: 主指标 - calendar 提效（不 clip）
  efficiency_ratio     = (T_baseline_calendar - T_actual_calendar) / T_actual_calendar
  efficiency_band_low  = (T_baseline_calendar_low - T_actual_calendar) / T_actual_calendar
  efficiency_band_high = (T_baseline_calendar_high - T_actual_calendar) / T_actual_calendar
  
  极端值不 clip，通过 outlier_flag 暴露

Step 3.5: 内部下钻 - work 提效（不向业务方暴露）
  work_efficiency_ratio = (T_baseline_work_fused - T_actual_work_corrected) / T_actual_work_corrected
  ⚠️ 公式分子必须是 total_active_work_corrected_min（§2.3.6b）
     仅作为算法工程师调试用，下钻看"为什么 calendar 和 work 差距"

Step 3: 置信度（综合多种信号，不只看 std）
  spread_ratio       = T_spread_work / T_baseline_work_fused
  
  feature_dep_risk   = high 任一触发：
                       · 单一特征贡献 ≥ 80%
                       · churn 率 ≥ 30%（add+remove vs net 比例）
                       · revert 比例 ≥ 20%（同文件被覆盖率）
                       · 生成后删除率 ≥ 15%（AI 生成且同 Need 内删除）
                       · 重复率 ≥ 40%（净增 LOC 中高相似度行）
  
  silica_signal           = 含硅量是否 ≥ 0.3（执行段反推有效性）
  
  ai_code_ratio_signal    = ai_code_ratio (= ai_covered_loc / 总 LOC) 是否 ≥ 0.3
                            含义：AI 代码占比，反映 session 内 AI 参与深度
  
  uncovered_work_signal   = uncovered_work_ratio (= uncovered_human_min / corrected_work) 是否 ≤ 0.3
                            含义：脱离 session 的裸 commit 工作量占比
                            
  ⚠️ ai_code_ratio 和 uncovered_work_ratio 是独立信号，不要混用：
     · 低 ai_code_ratio：session 内人工写得多 → AI 参与度信号弱
     · 高 uncovered_work_ratio：很多 commit 没 session 关联 → AI 提效信号弱
  
  confidence_level =
    "high"    if spread_ratio < 0.15 
              AND feature_dep_risk = low 
              AND silica_signal = pass
              AND ai_code_ratio_signal = pass
              AND uncovered_work_signal = pass
    "medium"  if spread_ratio < 0.30 AND no critical issues
    "low"     otherwise
  
  ⚠️ 注意：三方对照能抓"建模方式不同导致的偏差"，但抓不到"共同特征偏差"。
     LOC 被 AI 膨胀这种问题，三个方法会一起偏大——三方一致 ≠ 一定准。
     **人工 anchor 才是真正独立的信号**，必须保留作为终极对照。

Step 4: 业务展示字段
  实际开发跨度 = T_actual_calendar               （已是 calendar 尺度）
  古法估算跨度 = T_baseline_calendar             （= work / density，同 calendar 尺度）
  
  两者用同样的"含休息时间"尺度，可以直接对比给业务方看：
  "AI 让需求从 88h 古法跨度压到 25h"
```

输出主指标 `ratio` / `band` / `confidence` + 时间对比 `T_actual_calendar` / `T_baseline_calendar` + 内部下钻 `work_efficiency_ratio`。

### 4.8 Edge cases & Null 处理

| Case | 处理 |
|---|---|
| 新 Need 无任何特征 | `efficiency_ratio = NULL, reason = "no signal"` |
| `T_fused < 1 min` | NULL，避免分母过小爆炸 |
| 只有 1 个基线可用 | 单基线值 + `confidence = "low"` |
| 全部 3 个基线失败 | NULL，记 error log |
| `T_actual > 5 · T_fused` | 不 cap，但 `outlier_flag = true` |
| `T_actual < T_fused / 10` | 同上 outlier flag |
| Anchor 库为空（首次部署） | Baseline B 不参与融合，只跑 A + C |

所有边界 case 不抛异常，**记 reason 字段写入数据库**。

代码层面同一份实现，调用入口和后处理不同。

#### 6.2.1 提效比聚合时的低置信度处理

**`boundary_confidence ∈ {low, very_low}` 的 Need 不参与团队聚合统计**，但**必须同时展示覆盖率**避免选择偏差。

仪表盘团队报告字段：

```
team_report_week:
  efficiency_ratio = (Σ baseline_calendar_min - Σ actual_calendar_min) / Σ actual_calendar_min
                     ↑
                     calendar 维度，跟单 Need 主指标同一尺度
                     仅纳入 boundary_confidence ∈ {high, medium} 且 status = merged 的 Need
                     聚合前不算单 Need ratio，先 sum 分子分母再算
                     
  team_work_density_used  本周用的密度（最新快照）
  
  也可下钻看 work_efficiency_ratio:
    = (Σ baseline_fused_work_min - Σ total_active_work_corrected_min) / Σ total_active_work_corrected_min
    内部参考，反映"严格工作时间维度"的提效
                     
  coverage_high_confidence    high 置信度 + merged 工作量占比
  coverage_medium             medium 置信度 + merged 占比
  coverage_low_unreported     low + very_low 占比（不进 ratio）
  coverage_abandoned          status = abandoned 工作量占比（投入了但没上线）
  coverage_active             status = active 工作量占比（还在进行中，本周未结算）
  
  覆盖率约束：
    coverage_high + coverage_medium + coverage_low_unreported 
      + coverage_abandoned + coverage_active = 100%
    
警示线：
  · 如果 coverage_low_unreported > 40% → 整个 ratio 标 "可信度受限"
  · 如果 coverage_abandoned > 20% → 额外标记 "本周有显著失败工作量"
```

#### 6.2.2 abandoned Need 的闭环处理

`status = abandoned` 的 Need（force-pushed away、分支废弃、PR closed without merge）**仍然计算所有指标**，但：

- ✅ **进入覆盖率统计**（避免选择偏差："本周看似 17% 提效，但 25% 工作量是废弃的"）
- ❌ **不进入团队 efficiency_ratio 数字**（这些工作没产生交付价值）
- ✅ **保留单 Need 的 ratio 字段**供下钻分析（看 AI 在失败需求上的表现）
- ✅ 单独的"失败工作量"维度展示

举例展示：

> 本周团队提效 17%（基于 merged + 高置信度的 73% 工作量；其中 5% 因分支规范问题未归类、22% 是 abandoned 需求）

## 7. 防御机制

### 7.1 必做的防御

| 机制 | 说明 |
|---|---|
| **Hold-out validation** | anchor 集 80/20 切分，每周报告 hold-out MAE |
| **敏感性 flag** | `feature_dependency_risk = high` 任一触发：单特征贡献 ≥80%、churn 率 ≥30%、revert 比例 ≥20%、生成后删除率 ≥15%、重复率 ≥40%（防 AI 生成的样板/重复/先写后删污染基线） |
| **跨基线分歧 → 人工队列** | `T_spread / T_fused > 0.5` 时自动入队人工标注 |
| **时间衰减权重** | anchor 权重半衰期 6 个月，防老数据污染 |
| **Outlier flag without removal** | `T_actual > 5·T_fused` 或 `< T_fused/10` 只标记不删 |
| **聚合优先** | 单 Need ratio 不暴露给业务方，业务面看用户·周聚合 |
| **显式两档报告** | `ratio_conservative` 和 `ratio_optimistic` 随时可查 |
| **Need 长度上限** | > 30 天自动 split sub-need |
| **失败 Need 不剔除** | abandoned/force-pushed 标记 status 但仍参与统计 |

### 7.2 建议做（V1 可选）

| 机制 | 说明 |
|---|---|
| **季度对照采样** | 1-2 志愿者每季度做 1-2 Need 关闭 AI，spot-check |
| **时间固定效应** | 跑全团队学习曲线模型，剔除"团队成熟"部分再报 AI uplift |

## 8. 显式不解决（V1 范围外）

| 不解决项 | 理由 |
|---|---|
| 离线思考时间 | 物理上不可观测 |
| 跨 Need 知识迁移收益 | 单 Need 维度无法归因，需长周期跟踪 |
| PR reviewer 时间 | 数据可采但归因复杂，V2 |
| 多人协作 Need 的工时分配 | 简单平均失真，V2 |
| 不同 seniority 的 baseline 差异 | V1 统一假设"中级开发者"，V2 |
| 不同语言/技术栈的 baseline 差异 | V1 用全局系数，V2 按 repo / language 分系数 |
| AI 模型差异 (Claude vs GPT vs ...) | V1 不区分，V2 按 model 维度 |

**核心原则**：把这套系统定位为**中等粒度的方向指示器**，不是精确的工时计量。**不假装能做到后者。**

## 10. V1 验收标准

**核心原则**：验收**算法本身的正确性**，不验收"是否落在行业区间"——后者会鼓励调参到目标值，本末倒置。

### 10.1 算法正确性

1. **Hold-out MAE**：每个基线在 hold-out 20% anchor 集上的 MAE / median(human_labeled) ≤ **0.4**
2. **METR 拟合度**：在 METR 246 任务 hold-out 子集上，方法 A 的 MAE ≤ METR 自报的 between-developer 标准差
3. **可重跑稳定性**：同时间段重跑（anchor 库 / 系数不变时），所有 Need 的 `efficiency_ratio` 差异 ≤ 5%
4. **公式无塌缩**：
   - 人工构造极端测试用例（T_actual_calendar × 2，其他不变），验证 `efficiency_ratio` 单调递减
   - 验证 T_baseline_calendar = T_baseline_work / team_density 不出现退化（团队密度 ≠ actual 密度时 calendar 和 work 提效不应相等）
5. **古法系数合理性**：方法 A `lines_per_min` ≤ 0.5（必须明显慢于 AI 时代的 1.0，否则 baseline 偏低，提效虚低）

### 10.2 系统可观测性

5. **极端值可发现**：所有 `efficiency_ratio < -0.5` 或 `> 0.9` 的 Need 必须有 `outlier_flag = true` 且 `reason` 非空（不截断，但可发现）
6. **失败可观测**：所有 `efficiency_ratio = NULL` 的 Need 都有 `reason` 字段说明
7. **可下钻**：每条 Need 都能查到：三段时间 → 三基线值 → 融合权重 → 置信度依据
8. **置信度覆盖**：≥ 70% 的 Need 拿到 `confidence_level ∈ {high, medium}`

### 10.3 覆盖率（防止选择偏差）

9. **覆盖率字段必须存在**：每个团队周报告显式展示：
   - `coverage_high` ≥ 50%
   - `coverage_low_unreported` ≤ 40%
   - 否则整个 ratio 标 "可信度受限"

### 10.4 双轨兼容性

10. **旧路径无回归**：旧命令 `kbcli efficiency` 跑出来的 `user_productivity` 字段与改造前完全一致（bit-for-bit）
11. **新路径独立**：新命令 `kbcli efficiency-v2` 写入 `needs` / `user_productivity_v2` 表，不读取或修改旧表的写入逻辑
12. **`efficiency_mode = both`** 时两套数据并存且互不污染，可通过同一时间段两套数据 join 看差异

### 10.5 显式不验收（避免误导）

以下指标**不作为算法验收标准**，仅作为业务参考：

- ~~"团队 30 天总提效比落在 [5%, 25%]"~~ — 这会鼓励调系数到目标区间
- ~~"看起来合理"~~ — 主观、不可量化
- ~~"业务方满意"~~ — 跟算法正确性无关

业务方 KPI 走聚合层和趋势看，不进算法验收。
