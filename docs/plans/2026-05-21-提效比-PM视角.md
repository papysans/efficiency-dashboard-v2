> 配套文档：[详细公式版](./2026-05-21-提效比-design.md)

---

## 一句话

**用三种独立方法分别估"如果不用 AI 该花多久"，结果一致时报点值，结果分歧时报区间，"我不确定" 比 "强行报一个数" 更扛打。同时保留旧 LLM 估算系统作为旁路，新旧双轨并行。**

---

## 为什么要做

### 痛点 1：当前数字不能用 + 口径混乱

我们当前系统内部**两个地方用了两种不同公式**：

| 位置 | 公式 | 含义 | 例（ancient=4h，real=1h） |
|---|---|---|---|
| 后端 `CalcEfficiencyRatio` | `((ancient - real) / real) × 100` | 提升百分比 | **300%** |
| 前端项目详情页 | `ancient / actual` | 效率倍数 | **4x** |

两个数学上等价（300% = 4x - 100%），但**业务方一会儿看到 300% 一会儿看到 4x**，谁也搞不清楚谁是谁。

实际跑出来常见 **300%、500%** 这种数字（按百分比口径）。任何稍懂业务的人看一眼都知道不可能——业内最严谨的研究告诉我们，AI 端到端提效的合理范围是 **8% - 20%**：

| 来源 | 实测提效 |
|---|---|
| METR 246 任务随机对照实验（2025） | 开发者主观感觉快 20%，实测**慢 19%** |
| Thoughtworks 案例 | 编码环节快 30%，端到端 delivery 只快 **8%** |
| Bain Tech Report 2025 | 团队级提效 **10% - 15%** |
| 阿里灵码官方 | 编码占比 30% × AI 代码占比 40% = **12%** |

**超过 50% 几乎可以确定是公式错。**

#### 用户故事

> PM 小李想在周会上汇报"AI 给我们提效多少"。打开仪表盘看到"提效 487%"，下意识地——**不敢汇报**。她问开发：你们信吗？开发说：不信，但是数据就这样。这套系统就废了。

---

### 痛点 2：测错了对象

现在算的是"一段对话"的提效比。但开发者真正的工作流是：

> 头脑风暴 → 看代码 → 写方案 → 拆任务 → **写代码** → 验证

写代码只是中间一小段。AI 时代，写代码已经被压扁了，**真正花时间的是前置思考和后置验证**。但当前系统只看见中间那段。

#### 用户故事

> 工程主管小王问："我们用了 AI 一年了，为啥需求交付速度没变快？"答案藏在数据里没人看见——AI 把 1 小时的编码压到 10 分钟（看起来提效 90%），但前面 4 小时的思考和后面 1 小时的验证根本没动。整体只快了 17%，但系统只测中间那 10 分钟，所以显示"提效 90%"。

---

### 痛点 3：单一信任源

不论用 LLM 估、还是用规则估，本质都是"猜一个反事实"。这个反事实**不可观测**——METR 实测：开发者自己事后还坚信 AI 帮自己快了 20%，结果实测慢了 19%。**人对自己工作的反事实判断本身就偏差巨大**。

如果系统只有一个估算源，等于把整个度量体系的可信度押注在一个估算上。一旦被质疑，没有第二个声音支持。

#### 用户故事

> 老板看到提效报告问"这数据怎么来的"。开发回答"调 GPT 估的"。老板心里咯噔——**这就是单一信任源的脆弱性**。

---

## 解法的思路

### 三个关键转变

| 转变 | 旧做法 | 新做法 |
|---|---|---|
| **度量单位** | 一段对话（task） | 一个需求（need = git 分支） |
| **测量范围** | 只看编码环节 | 把会话切成"思考 / 执行 / 验证"三段，全部测量 |
| **基线来源** | 单一 LLM 估算 | 三种独立方法估算 + 互相校验 |

### 公式形态也变了

新公式直接用 **calendar 维度**（含吃喝拉撒睡觉），跟"几天能做完"的日常直觉对齐：

```
提效比 = (古法估算跨度 - 实际开发跨度) / 实际开发跨度
       = (88h - 25h) / 25h
       ≈ 2.52  即 252%
```

两个时间都是 calendar 尺度，含睡眠周末，可以直接对比。

#### 古法估算跨度怎么算

```
1. 三方法估出"古法工作时间" = 22h
   （敲键盘+查资料+调试的总时间，不含睡眠）

2. 用"团队工作密度"反推 calendar 跨度
   团队历史显示：开发者平均每天工作 6 小时（剩下 18h 吃饭睡觉）
   工作密度 = 6/24 = 25%
   
3. 古法 calendar 跨度 = 古法工作时间 ÷ 工作密度
                     = 22h / 0.25 = 88h ≈ 3.7 天
```

**核心假设**：古法做这个需求，开发者吃饭睡觉的节奏跟现在一样（AI 不会让你少睡觉）。所以同样的工作量 22h，按团队每天 6h 工作的节奏，要花 88h calendar。

**数字怎么解读**："AI 把古法 3.7 天的需求压成 1 天交付，相当于提效 252%（古法用了 AI 的 3.5 倍时间）"——业务直观。

**读法速查**：
- `0` = 没提效（古法 = AI）
- `1` = 提效 100%（古法用 AI 的 2 倍时间）
- `4` = 提效 400%（古法用 AI 的 5 倍时间）
- `-0.5` = 反向，AI 反而花了古法的 2 倍时间

**数学性质**：上限无穷（古法相对 AI 的倍数可以越来越大），下限 -1（AI 拖死人）。不截断，极端值通过 `outlier_flag` 标记。

业务方看聚合数字（先 sum 分子分母再算），单条 Need 极端值不污染整体。

## 完整用户故事：周一上午，小李做完一个需求

**需求**：把订单中心的状态机重构。

**过程**：从周一到周三花了 3 天，期间开了 5 个 Claude 会话，写了 12 个 commit，最后 merge 到主分支。

### 系统在小李 merge 后自动跑

#### 第 1 步：识别"需求"

检测到 `feature/order-state-refactor` 这个 git 分支，从第一次 push 到 merge 共 3 天，识别为一个完整需求。

#### 第 2 步：聚合 5 个会话

把这 3 天里小李的所有 Claude 会话都归到这个需求名下。会话可以跨天、可以中间隔了几个小时——只要 commit 推到这个分支，就归到这个需求。

#### 第 3 步：每个会话按事件类型逐条归属

旧版"按时间段切大段"的做法会把 `edit → test → edit` 循环里的 test 全归执行段，**严重低估验证段**。新做法按事件类型逐条打标签：

- **思考段事件**：纯对话、Read、Grep、WebFetch/Search、ExitPlanMode、TodoWrite（且没进入执行期）
- **执行段事件**：Edit / Write / NotebookEdit / MultiEdit 等"产出代码"的工具调用
- **验证段事件**：在执行期内，每次 Edit 后到下次 Edit 前的 test / build / typecheck / lint 等；最后一次 Edit 之后所有事件

**举例**：

```
[10:00] 用户："我要加个忘记密码"   ← 思考
[10:03] Read auth.go              ← 思考
[10:08] Edit auth.go              ← 执行
[10:12] Bash "go test"            ← 验证（虽然在执行期内，但 test 算验证）
[10:14] Edit auth.go (修 bug)      ← 执行
[10:16] Bash "go test"            ← 验证
[10:18] Edit reset_pwd.go          ← 执行
[10:30] Bash "go test" 通过        ← 验证（终极验证）
```

汇总：
- **实际工作时间**（session active 累计）：**5 小时**
- **实际开发跨度**（含一个隔夜睡眠）：**25 小时 ≈ 1 天**
- **三段分布**：思考 2h05、执行 1h35、验证 1h10

> **简化假设**：单人需求、无裸 commit、AI 代码占比 0.79。多人协作或有裸 commit 时按 §2.3.6/§2.3.6b 做 person-time 和裸 commit 反推。

#### 第 4 步：三种方法分别估"如果不用 AI 该花多久"

> ⚠️ 这里的估算是**古法工作时间**（敲键盘+调试+查资料的总时间，不含睡眠）。系数从 METR without-AI 数据拟合，比 AI 时代慢约 5 倍。

| 方法 | 怎么估 | 古法工作时间 |
|---|---|---|
| 方法 A：规则模型 | 120 行 × 古法速率 0.2 行/分钟 + 思考 + 验证 | 24 小时 |
| 方法 B：找相似需求对比 | 在样本库找特征最像的 5 个 METR 任务 | 20 小时 |
| 方法 C：让 LLM 估 | 给 Claude 看结构化摘要直接估 | 25 小时 |

三个估算互相校验，**融合 ≈ 22 小时**，分歧 std 2.5h（约 11%，分歧不大）。

#### 第 5 步：把古法工作时间换算成 calendar 跨度

```
团队工作密度 = 0.25（团队历史平均，每天工作 6h）

古法 calendar 跨度 = 22h / 0.25 = 88h ≈ 3.7 天
```

#### 第 6 步：算最终提效比

```
提效比 = (古法估算跨度 - 实际开发跨度) / 实际开发跨度
       = (88h - 25h) / 25h
       ≈ 2.52  即 252%
```

三种方法分歧小 + 含硅量 + AI 代码占比 + 无裸 commit → **置信度"高"**

区间：**约 220% ~ 290%**

#### 第 7 步：小李在仪表盘看到

```
feature/order-state-refactor
─────────────────────────────────────
提效 252% (区间 220% ~ 290%)，置信度高

⏱ 时间对比：
  实际开发跨度：25h ≈ 1.04 天
  古法估算跨度：88h ≈ 3.7 天
  → AI 把 3.7 天的活儿压成 1 天交付

🔍 阶段分布（按 work 时间）：
  思考 2h05  ████  (42%)
  执行 1h35  ███   (32%)
  验证 1h10  ██    (24%)

✅ 信号检查全部通过
```

#### 小李的洞察

执行环节 + 验证环节合起来才占 56%——思考占了 42%。**下次试试让 AI 帮自己提前梳理需求，把思考阶段压一压**。

业务方汇报：

> "AI 帮我们把一个原本 3.7 天的需求压到 1 天交付，提效 72%。"

**这种数字比"提效 487%"靠谱得多——是 PM 真的敢拿出去汇报的数字**。

## 关键设计点（白话版）

### 1. 为什么用"需求"作为度量单位

**实际场景**：一个需求经常横跨多个会话。如果按对话算，等于把一个需求切碎了报。

**设计**：一个 git 分支 = 一个需求。多个会话、多个 commit 都归到这个需求下。

**好处**：

- 汇总成"做完这件事快了多少"才是业务直觉
- 单个对话再 trivial（5 秒搞定）也不会单独造成异常值
- 业务方关心的是"需求交付速度"，刚好对齐

#### 但是开发的人不总是老实开分支怎么办？

现实里有人直接 commit 到 main、有人一个长期分支做 N 个需求、有人 commit message 写"fix"啥都看不出。只靠 branch 识别 Need 大概只能覆盖 60-70%。剩下的靠**多信号 fallback 链**：

```
1. 优先：一个 PR = 一个需求
2. 其次：一个非主干 git 分支 = 一个需求
3. 再次：commit message 里的 issue 号（#1234 / JIRA-123）= 一个需求
4. 兜底：同一个人 7 天内动一批相关文件 = 一个需求
5. 实在不行：按"用户·周"打包成"未归类活动"
```

每个需求记录它是哪一级识别出来的，标注**置信度**：

- 1、2 级 → 高置信度（进团队聚合统计）
- 3 级 → 中
- 4、5 级 → 低 / 极低（**不进团队聚合报告**，仪表盘单独有"未归类活动"维度展示）

对不规范的开发者，提效比测不准是正常的。系统坦白说"不知道"比硬猜一个数字好。

#### 等 reviewer merge 的时间不算开发时间

如果你周三完工但 reviewer 周日才 merge，**这段等待不应该算到提效比里**。

设计上把时间彻底拆开：

| 字段 | 含义 |
|---|---|
| `T_actual_work_corrected` | ★ **进提效比公式**：每个贡献者 active 时间求和（person-min）+ 非 AI 裸 commit 的反推工作时间 |
| `T_actual_wall` | 各 session 时间区间并集（wall-clock），仅 display |
| `T_actual_calendar` | 日历跨度（含吃饭睡觉周末，剔除 > 3 天搁置），仅 display |
| `dev_duration_min` | 开发周期（开始到完工） |
| `cycle_duration_min` | 完整周期（开始到上线） |
| `wait_for_review_min` | review 等待时长（**单独统计，不进提效比**） |

#### 关键概念：person-time 进公式，wall/calendar 仅 display

- **公式分子要跟基线概念对齐**：基线来自 METR，是 person-hours（单人工作量）。所以分子也必须是 person-time，不能用 wall-clock。
- **多人协作 case**：两个人各干 1h，按 person-min 算 = 120min（正确），按 wall-clock 并集算 = 60min（错，会假提效 50%）。
- **日历跨度**：含睡觉吃饭，是"开发周期感"信号，**不能跟工作时间直接对比**——一个是含睡眠的墙钟，一个是连续工作量。

#### 漏算修正：非 AI 人工工作也得算

如果开发者大部分时间在 IDE 手写、查资料、开会，最后 commit 进来，AI session 只占小部分——这时候 baseline LOC 大、actual session active 小，提效比虚高。

修正用**两个独立信号**：

```
信号 1：AI 代码占比（ai_code_ratio）
  = 含硅量匹配到的 LOC / 总 LOC
  反映：session 内 AI 帮忙写代码的深度

信号 2：裸 commit 工作量占比（uncovered_work_ratio）
  裸 commit = 时间窗口 + 文件交集都对不上任何 session 的 commit
  uncovered_work_ratio = 裸 commit 反推工作时间 / 总 corrected 工作时间
  反映：开发者在 Claude 之外完成的工作量

两者独立，不可混用：
  · 低 ai_code_ratio：session 内人工写得多 → AI 参与度信号弱
  · 高 uncovered_work_ratio：很多 commit 没 session 关联 → AI 提效信号弱
```

T_actual_work_corrected 加上裸 commit 反推：

```
T_actual_work_corrected = session 期间 active 时间（含全部贡献者）
                        + 裸 commit 部分按古法速率反推
                        
含义："承认这块裸 commit AI 没帮，按古法速率算 actual 投入"
```

任一信号低于阈值 → 降级置信度。

#### 古法工作量怎么展示

业务方仍想看"AI 用了多久 vs 古法估算多少工作量"对比。但 PM 视角的"实际跨度 1 天 vs 古法 0.7 天"这种数字直接对比会误导（一个含睡眠墙钟、一个连续工作量）。

V1 的展示方式：

```
实际开发跨度（含休息）  : 1.04 天
古法工作量折算          : 约 0.7 工作日
⚠️ 两者不可直接对比——时间尺度假设不同
```

V2 可能用统一工作日历从相同起点排程出真正可比的日历时间，但 V1 不做。

### 2. 为什么切三段（思考 / 执行 / 验证）

**分段规则全部由数据自动判断，零 LLM 介入**：

- 改代码是"产出动作"，其他都是过程
- **开始动手之前 = 在想**
- **动手期间 = 在做**
- **动完之后 = 在检查**

这是数据里最稳定的物理边界。

**好处**：
- 验证用户直觉"上游贵 / code 便宜"是否真的成立
- 瓶颈一目了然
- 不同人的工作风格能各自如实呈现（有人 80% 时间在思考，有人 80% 在执行，都合法）

---

### 3. 三种方法估"不用 AI 该花多久"

#### 方法 A：混合估算（思考/验证靠经验，执行段直接反推）

像工厂里给每道工序定标准工时，但**三个段的估算方式本质不同**：

| 段 | 估算方式 | 凭据 |
|---|---|---|
| **思考段** | 经验估算 | 读了多少文件、对话几轮、输入多少字 × 历史单价 |
| **执行段** | **直接反推** | 真实改了多少行代码、多少文件 × "老师傅每行多久"（精确） |
| **验证段** | 经验估算 | test 跑几次、改 bug 几次 × 历史单价 |

**执行段比其他两段可信得多**，因为它有"硬产出"——diff、commit、改了哪些文件，这些都是事实，不是过程信号。

**精确到代码行的归属**：现有系统已经有"含硅量（silica）"机制——每一行代码都通过指纹（hash）匹配，**精确知道是 AI 生成的还是人手写的**。这套机制天然支持执行段反推：

- 假设全部代码人手写需要多久 = 执行段古法基线
- 已经被 AI 写的部分（含硅量高）说明 AI 帮的多，提效信号强
- 如果含硅量很低 → AI 没怎么帮 → 即使提效比算得高也要打折扣

**单价从哪来**：用 **METR 公开的 246 个任务数据集**作为种子拟合系数。这个数据集每个任务都有"用 AI"和"不用 AI"两套真实测量时间，是目前业界最严谨的 AI 提效实测（独立研究机构 METR 做的随机对照实验，已开源到 GitHub）。

**重要**：执行段公式直接复用现有 `algo_estimator.go::estimateCommitAncientMinutes` 的核心反推逻辑，只是叠加 files / complexity / 迭代次数等新维度。**不是另起炉灶**。

#### 方法 B：找相似需求对比

把新需求的特征（代码量、文件数、对话长度等）算出一个"特征指纹"，去样本库里找最像的 5-10 个，按相似度加权平均它们的"不用 AI 时间"。

**样本库怎么建**：
- 第一批：METR 的 246 个真实测量任务
- 第二批：团队内部如果有人工标注的需求，也加进来
- 越用越大，越大越准

#### 方法 C：让 LLM 看摘要估（成本受控）

**注意**：不是把整个会话原文丢给 LLM——长会话几 M token 直接喂，成本爆炸。

实际做法：先把每个会话压成一句话摘要（用 Haiku 等小模型，离线生成）；然后把整个需求的结构化摘要（活跃时间、三段分布、产出量、关键决策、各会话一句话摘要）拼起来扔给 LLM，让它估"不用 AI 该多久"。

```
输入约 1500 字 → LLM 估算 → 输出 200 字
单次成本约 ¥0.005
一个需求只调一次（不是每会话一次）
成本与会话数无关
```

**为什么保留**：作为第三个独立信号源。三方对照比单一信号更可信。即使它有时不准，也会被自动降低权重，不会污染整体结果。

---

### 4. 三种方法互相校验，融合成最终结果

**每周后台跑一次**：

1. 拿系统里所有"人工标过真实耗时"的样本
2. 看三种方法各自估得多准
3. **估得准的方法权重高，估得差的方法权重低**
4. 这个权重不是人拍的，是数据自动算的

**好处**：不需要业务方信任任何一个方法。三方对照后偏差自然被抑制。

---

### 5. 不确定时坦白说"不确定"

每个需求的提效比都带三件套：

| 字段 | 例子 | 含义 |
|---|---|---|
| **数字** | 18% | 三种方法融合后的点估计 |
| **区间** | 12% ~ 25% | 三种方法分歧形成的不确定带宽 |
| **置信度** | 高 / 中 / 低 | 三种方法之间的一致程度 |

**业务方看到"低置信度"会自动谨慎**，比拿一个看似精确的数字去汇报安全得多。

## 双轨并存：保留旧 LLM 估算系统

按业务要求，**现有 LLM 估算路径完整保留**，作为新算法系统的独立旁路。

### 双轨架构

```
                    Claude 会话数据
                          ↓
                    ┌─────┴─────┐
                    ↓           ↓
              新算法系统       旧 LLM 估算
              （需求维度）     （对话维度）
                    ↓           ↓
            三方法融合         单值 ancient_minutes
            含区间和置信度     task 级提效比
                    ↓           ↓
                  需求表       保留 tasks 表
                    ↓           ↓
                    └─────┬─────┘
                          ↓
                    仪表盘双视图
```

### 切换与对比

- 配置开关：`efficiency_mode = new | legacy | both`
- 默认 `both`：两套并行跑，仪表盘可切换视图
- 业务方质疑新系统时，老 LLM 结果随时可调出对照
- 长期累积可对比"新系统融合 vs 老 LLM 单估"哪个更准

### 旧系统具体保留什么

- `cmd_efficiency.go` 的所有聚合函数全保留
- 公式仍然按对话维度，实际是 `((ancient - real) / real) * 100`（提升百分比口径，例 4h 估算 vs 1h 实际 → 300%）
- v1/v2/v3 三种 prompt 保留，可配置选用哪版
- 写入 `user_productivity` 表的字段不动

### 新系统新增什么

- 新表：`needs`、`session_stage_metrics`、`anchor_set`、`baseline_coefficients`、`baseline_fusion_weights`
- 新命令：`kbcli efficiency-v2`（不覆盖旧 `efficiency` 命令）
- 新 API：`/api/v2/needs`、`/api/v2/efficiency`

### 双轨使用场景

#### 用户故事：老板找小李对账

> 老板："上个月 AI 提效到底多少？"
>
> 小李：（打开仪表盘新视图）"融合算法说 14%，置信度高。"
>
> 老板："你这数字怎么来的？老的那个不是说 200%吗？"
>
> 小李：（切回老视图）"老的是按对话算的纯比值，没有上下界，trivial 任务会失真。这是同一份数据按新方法算的。三种方法互相对过。"
>
> 老板：（点点头）"以后默认看新的。老的留着以防有人质疑。"

#### 用户故事：算法工程师做对比研究

> 算法工程师小张想看新旧系统的差异规律。打开数据库，把同一时间段的 `tasks.task_efficiency_ratio` 和 `needs.efficiency_ratio` join 起来——发现 trivial task 上两套差异最大，复杂需求上反而比较一致。**这种洞察反过来又帮助新系统调参**。

## 这套系统测不到什么（先把丑话说在前面）

| 测不到的东西 | 后果 |
|---|---|
| 洗澡 / 散步 / 开会想需求的时间 | 实际时间偏低，提效比偏高 |
| Slack 讨论、读外部文档、纸笔思考 | 同上 |
| PR 评审同事花的时间 | 只算了作者，少算了协作者 |
| 跨需求知识迁移（这个需求学了，下个需求快了） | 收益归错地方 |
| AI 生成了冗余代码导致代码行数虚高 | 估算时间被高估，提效比被高估 |
| 没合并的需求（被废弃 / force push 掉的） | **已闭环**：abandoned Need 仍然算所有指标，进入覆盖率统计但不进 efficiency_ratio。仪表盘单独展示"失败工作量占比"，防止团队 ratio 偏乐观 |

**核心原则**：把这套系统定位为"中等粒度的方向指示器"，不是"精确工时计量"。

- 看团队趋势 ✅
- 看部门间对比 ✅
- 看个人考核 ❌（个体差异 + 噪声太大）

## 这套系统怎么自我修复

### 必做的防御机制

#### 1. 每周拿"留一份"样本独立验证

把人工标过的样本随机切 80/20：训练只用 80%，剩 20% 当成"考试题"，报告各方法在考试题上的误差。**这是诚实的泛化误差**，是业务方质疑时的客观答案。

#### 2. 三方分歧大的需求 → 自动入人工队列

当三种方法估的差距大于一倍时，系统主动标记，邀请人工看一眼实际耗时多少。这些人工反馈又会回流到样本库。**样本库越用越大，越大越准。**

#### 3. 老数据自动减重

6 个月前的样本权重打半折，防止 2025 年的 Claude 3.5 数据污染 2026 年 Claude 4.7 时代的估算。

#### 4. 极端值标记不删

实际比估算长 5 倍、或短 10 倍的需求，标记为"异常"但不删除。可能是真实信号（**METR 已经证实过 AI 真的让一些人变慢**）。

#### 5. 业务面只看聚合数字

单个需求的提效比仅作开发自己看。汇报场景看用户·周聚合后的数字（先把分子分母分别加起来，再算总比例）。

---

### V1 不做的事

刻意不做，避免无穷工程化：

- 不补离线思考时间（这不是脑波仪）
- 不归因跨需求迁移收益
- 不分摊多人协作时间
- 不按经验级别建模（初级 vs 资深统一假设"中级"）
- 不按语言 / 技术栈建模（V1 全局系数）
- 不区分 Claude / GPT 等模型差异

V2 再说。

## 数据流（对齐现有模式）

新系统数据流与旧系统形状一致：**从下游捞数据，往上游送结果**。

```
下游表（不变 + 扩展）
  · 对话与消息表
  · 工具调用表（新增，含时间戳与 payload）
  · commit / PR 表
       ↓
Step 1: 每个会话算特征 + 三段活跃时间 → 会话指标表
       ↓
Step 2: 按 git 分支聚合多个会话 + commit → 需求表
       ↓
Step 3: 三种方法并行估算 → 各自的"不用 AI 时间"
       ↓
Step 4: 融合 + 算提效比 + 算区间 → 写入需求表
       ↓
上游表
  · 需求表（带提效比 / 区间 / 置信度）
  · 用户·周聚合表（业务汇报口径）

后台周期任务（每周一次）
  · 重算各方法的历史误差，更新融合权重
  · 用内部数据小步修正方法 A 的系数（防止漂移到团队相对值）
  · 6 个月前样本权重自动衰减
```

## V1 验收标准

**核心原则**：验收算法本身的正确性，**不**验收"是否落在行业区间"——后者会鼓励调系数到目标值，本末倒置。

### 算法正确性
1. **泛化误差小**：每种方法在留一样本上的 MAE / 中位真实耗时 ≤ 40%
2. **METR 拟合度**：在 METR 246 任务子集上方法 A 的 MAE ≤ METR 自报的人际差异标准差
3. **可重跑稳定性**：同一时间段重跑，所有需求的提效比差异 ≤ 5%
4. **公式无塌缩**：人工构造极端测试用例（实际工作时间翻倍，其他不变），提效比必须单调下降

### 系统可观测性
5. **极端值可发现**：所有 ratio > 90% 或 < -50% 的需求都有 `outlier_flag` 标记 + 非空 `reason`
6. **失败可观测**：所有空值都有原因字段说明
7. **可下钻**：每条需求都能查到"三段时间 → 三方法 → 融合 → 置信度依据"
8. **置信度覆盖**：≥ 70% 需求拿到"高"或"中"置信度

### 覆盖率（防选择偏差）
9. **覆盖率必须展示**：每个团队周报告显式展示 "本周 X% 工作量进入高置信统计"。`coverage_high + coverage_medium` ≥ 60%，否则整个数字标"可信度受限"

### 双轨兼容
10. **旧路径无回归**：旧命令字段写入与改造前完全一致
11. **新旧不互污**：双轨开启时两套数据独立

### 显式不验收
- ~~"团队 30 天总提效比落在 5%-25%"~~ — 会鼓励调系数到目标区间
- ~~"业务方满意"~~ — 跟算法正确性无关
