# 提效比度量体系 v2 · 端到端走查示例

> 状态：示例文档
> 日期：2026-05-21
> 配套文档：[详细公式版](./2026-05-21-提效比-design.md) · [PM 视角版](./2026-05-21-提效比-PM视角.md)
> 阅读对象：所有人
> 用途：用一个具体需求走完整套计算流程，验证设计逻辑

---

假设场景：你周一接到一个需求 "**给登录页加个忘记密码功能**"。下面一步步看系统在背后干什么。

---

## 周一 9:30 — 你开分支

你 `git checkout -b feature/forgot-password`，开干。

**系统这时候在干什么**：没干啥，就是默默盯着你这个分支。它知道**未来这个分支上发生的所有事情，会归到一个需求里**。

> **注**：这是"理想情况"，开发的人老实开了分支。如果有人不开分支（直接 commit 到 main、或者一个分支做多个需求），系统会走 fallback 链识别需求边界——见 [详细公式版 §2.3](./2026-05-21-提效比-design.md#23-need-边界识别)。简单说：**优先 PR、其次分支、再次 issue 号、兜底用文件聚类**，识别不出来的活动单独打 "未归类" 标签，不进团队统计。

---

## 周一 10:00–12:00 — 第一个会话，纯看代码、想方案

你打开 Claude，问"现有登录页怎么写的"。Claude 帮你 Read 了 8 个文件、Grep 了几次、你们讨论了 3 个方案最后选了一个。**整个会话没让 AI 动过一行代码**。

**系统记录的原始数据**：
- 会话 ID、开始 10:00、结束 12:00
- 35 轮对话
- 8 次 Read、12 次 Grep
- **0 次 Edit/Write** ← 这是关键
- 你输入了 4200 字
- 烧了 1.2M token

**系统怎么切段**：
- 找第一次 Edit/Write → 没找到
- → **整个会话被划为"思考段"**
- 活跃时间约 1h50min（中间你接了个电话停了 10 分钟，被 gap merge 剪掉了）

---

## 周一 12:00–14:00 — 午饭

系统：没动静，跳过。

---

## 周一 14:00–16:00 — 第二个会话，开干

你回来跟 Claude 说"开始写吧"。

- 14:05 让 Claude 写第一个文件 → **这是第一次 Edit/Write，记下时间戳**
- 14:05–15:55 期间你让 AI 改了 4 个文件，总共 +120 行 -15 行
- 15:55 最后一次 Edit → **记下时间戳**
- 15:55–16:00 你让 Claude 解释了一下其中一段逻辑（没改代码）

**系统怎么切段**：
- 思考段 = 14:00 → 14:05 = 5 分钟
- 执行段 = 14:05 → 15:55 = 1h50min
- 验证段 = 15:55 → 16:00 = 5 分钟

**16:10 你 commit + push**。系统看到这个 commit 推到 `feature/forgot-password` 分支，**把这次会话和 commit 都挂到这个需求名下**。

---

## 周二 10:00–11:00 — 第三个会话，修测试

跑测试发现两个 case 挂了。让 Claude 修。中间改了 2 次代码、跑了 3 次测试、又改了 1 次。

**系统记录**：
- 思考段 ≈ 10 分钟（一开始描述 bug）
- 执行段 ≈ 30 分钟
- 验证段 ≈ 20 分钟（最后那次跑测试通过 + 让 AI 自检了一下）

10:50 再 commit + push。系统继续挂到同一个需求。

---

## 周二 11:00 — 你开发完工

最后一个 session 结束（10:50 push 后没再开新会话）。系统把 **`dev_end_ts = 周二 11:00`** 记下：开发已完工。

## 周三 11:00 — reviewer 终于 merge 了

systems 记录 **`merge_ts = 周三 11:00`**，同时算出：

- `wait_for_review_min = 24h`（周二完工到周三 merge 之间纯等待）
- 这 24 小时**不算到提效比里**（提效比只看你 session 内的 active time）
- 但作为独立的"协作信号"展示

**这个需求"封闭"了**。开始结算。

---

## 系统怎么算（这就是核心）

### Step 1：把这个需求的所有东西汇总

- 3 个会话、2 个 commit、1 个 PR
- 单人需求，contributor 只有小李

**person-time（进公式）**：
- 各 session active 求和（gap-merged）= 1h50min + 2h + 1h ≈ **5 小时**

**wall-clock（仅 display）**：
- 各 session 时间区间并集 ≈ **5 小时**（单人 Need，跟 person-time 相同）
- 如果是多人协作：person-min 用求和、wall 用并集，**不能混**

**日历跨度（仅 display）**：
- 周一 10:00 → 周二 11:00 = 25h（含一个隔夜）
- 中间所有 gap ≤ 3 天，整段算入
- **T_actual_calendar = 25h ≈ 1.04 天**

### Step 1.5：检查两个独立信号（漏算修正）

**信号 1：AI 代码占比**

```
ai_covered_loc = 含硅量匹配到的 LOC = 95 行（120 行总改动里 95 行被 AI 指纹匹配）
ai_code_ratio  = 95 / 120 = 0.79（高，session 内 AI 参与深度好）
```

**信号 2：裸 commit 工作量占比**

```
裸 commit 判定（窗口 + 文件交集都对不上 session 的 commit）：
  本例两个 commit 都在小李 Claude session 时间窗口内 + 编辑文件有交集
  → 都是 session 关联，不是裸 commit
uncovered_loc = 0
uncovered_human_min = 0
```

**T_actual_work_corrected** = 5h (session active person-min) + 0min (无裸 commit) = **5h**

两个信号都通过：
- `ai_code_ratio = 0.79 ≥ 0.3` → pass
- `uncovered_work_ratio = 0 / 5h = 0 ≤ 0.3` → pass

### Step 2：把三段时间分别加起来（按 work 维度）

| 段 | 活跃时间 |
|---|---|
| **思考** | 1h50min + 5min + 10min ≈ **2h 5min** |
| **执行** | 0 + 1h50min + 30min ≈ **2h 20min** |
| **验证** | 0 + 5min + 20min ≈ **25min** |

你一眼看出：**思考和执行差不多平分，验证占小头**。这就比"一个会话总时长"信息量大多了。

### Step 3：三种方法分别估"不用 AI 该花多久"

**方法 A（混合：思考/验证靠经验，执行段反推）**：

| 段 | 估算方式 | 计算 | 结果 |
|---|---|---|---|
| 思考段 | 经验估算（古法） | 8 文件 × 30min 精读 + 写方案 + 决策 | ≈ 8h |
| **执行段** | **反推（古法系数）** | 120 行 ÷ 0.2 行/min + 4 文件协调 2h + 复杂度修正 1h + 迭代 1h | ≈ 14h |
| 验证段 | 经验估算（古法） | 古法手动 test + debug | ≈ 2.5h |

**执行段反推怎么走的**（这是最可信的一段，专门拆开看）：

```
Step 0: 过滤污染源
        从 120 LOC 里剔除 lock 文件、generated code、formatter 等
        本例假设无污染，120 LOC 全部计入

Step 1: 拉 need 关联的 2 个 commit
Step 2: 对每个 commit 调 estimateCommitAncientMinutes(totalLines, profile="balanced")
        commit_1: 80 lines / 0.2 line/min = 400min ≈ 6.7h
        commit_2: 40 lines / 0.2 line/min = 200min ≈ 3.3h
        小计：10h（假设全部古法手写所需时间）

Step 3: 叠加新维度修正
        + 4 files × 30min file_coordination = 2h
        + complexity_delta × factor = ~1h
        + re_edit_count × penalty = ~1h
        合计：约 14h（执行段古法基线）

Step 4: 含硅量 sanity check
        totalSilica = 0.65（AI 写了 65% 的代码）
        > 0.3 阈值，通过
```

- **方法 A 总估算 ≈ 24 小时**

注：执行段是真的"反推"（基于硬产出），思考/验证段是"经验估算"（基于过程信号）。

**方法 B（找相似需求对比）**：
> 历史上做过类似规模的"小功能新增"需求是几小时？

- 在样本库里找最像的 5 个（特征：约 120 行代码、4 个文件、中等对话量）
- 它们标注的"不用 AI 时间"分别是 18h、22h、19h、21h、20h
- 加权平均 ≈ **20 小时**

**方法 C（让 LLM 看摘要估，成本受控）**：

> 不是把整个会话原文丢给 LLM——长会话几 M token 直接喂成本爆炸。
> 实际做法：先用 Haiku 等小模型把每个会话压成一句话摘要（离线生成），然后把整个需求的结构化摘要（三段分布 + 产出量 + 各会话一句话摘要）拼起来一次性喂给 LLM。

输入约 1500 token、输出约 200 token、单次成本约 ¥0.005，**整个需求只调一次**。

- Claude 看完估 **25 小时**

### Step 4：融合三个估算（工作时间维度）

系统看过去三个方法在历史样本上谁更准。假设：
- 方法 A 历史平均误差 30%
- 方法 B 历史平均误差 20%（最准）
- 方法 C 历史平均误差 35%

**越准的权重越大**。融合后**古法工作时间**：

```
T_baseline_work = 24 × 0.3 + 20 × 0.45 + 25 × 0.25 = 22.45h ≈ 22 小时
spread = std{24, 20, 25} ≈ 2.5h
spread_ratio = 2.5 / 22 ≈ 11%
```

### Step 5：把古法工作时间换算成 calendar 跨度

```
团队工作密度 = 0.25（团队历史平均，每天 6h 工作）

古法 calendar 跨度 = 22h / 0.25 = 88h ≈ 3.7 天
```

### Step 5.5：算最终提效比（calendar 维度，主指标）

```
提效比 = (古法估算跨度 - 实际开发跨度) / 实际开发跨度
       = (88h - 25h) / 25h
       ≈ 2.52  即 252%
```

**解读**：AI 把古法 3.7 天的需求压成 1 天交付，相当于提效 252%（古法用了 AI 的 3.5 倍时间）。**符合直觉**：120 LOC + 4 文件的小功能，古法需要小半周（含探索、debug、testing），AI 让你一天搞完。

### Step 6：算置信度和区间

三个估算工作时间的差距：24h、20h、25h → 标准差约 2.5 小时。

- **spread_ratio**：2.5 / 22 ≈ 11% < 15% → 满足 "高" 的 spread 条件
- **silica signal**：totalSilica = 0.65 ≥ 0.3 → pass
- **ai_code_ratio signal**：0.79 ≥ 0.3 → pass
- **uncovered_work_signal**：0 ≤ 0.3 → pass
- **feature_dependency_risk**：churn 率、revert 率、生成后删除率都低 → low
- 全部通过 → **置信度"高"**

区间（在 baseline_calendar 上加减 spread 换算）：
- baseline_calendar_low  = (22 - 2.5) / 0.25 = 78h
- baseline_calendar_high = (22 + 2.5) / 0.25 = 98h
- **下界**：(78 - 25) / 25 ≈ 2.12（即 212%，基线偏低时）
- **上界**：(98 - 25) / 25 ≈ 2.92（即 292%，基线偏高时）

### Step 7：work 提效作为内部下钻字段

```
work 提效 = (T_baseline_work - T_actual_work) / T_actual_work
         = (22 - 5) / 5
         ≈ 3.40  即 340%
```

**为什么 calendar 提效（252%）比 work 提效（340%）低**？

因为 actual 这个 case 的工作密度（5/25 = 0.20）低于团队平均（0.25）——你跨夜了，calendar 上被"睡眠时间稀释"，所以 calendar 维度的提效数字比 work 维度更保守。这是真实的"跨夜成本"，不是 bug。

## 最终系统给你一行字

```
feature/forgot-password
─────────────────────────────────────
提效 252% (区间 212% ~ 292%)，置信度高

⏱ 时间对比（calendar 维度，业务方看）：
  实际开发跨度：25h ≈ 1.04 天（含一夜睡眠）
  古法估算跨度：88h ≈ 3.7 天
  → AI 把 3.7 天的活儿压成 1 天交付

📊 公式细节：
  T_actual_calendar     = 25h
  T_baseline_calendar   = 88h（= 22h / 0.25 团队密度）
  
  T_actual_work         = 5h
  T_baseline_work       = 22h（三方融合）
  team_work_density     = 0.25（每天工作 6h）

  方法 A: 24h | 方法 B: 20h | 方法 C: 25h
  spread = 2.5h（11%）

🔍 阶段分布（active time，事件类型归属）：
  思考 2h05  ████  (42%)
  执行 1h35  ███   (32%)
  验证 1h10  ██    (24%)
  OTHER 0h10 ░    (3%)

✅ 信号检查全部通过

下钻字段（默认不显示给业务方）：
  work 提效 = 340%（比 calendar 提效高 88 点 = 跨夜代价）
```

这个例子有几个有意思的点：

1. **提效 72%，业务直观**："AI 让 3.7 天的需求 1 天交付"——比"提效 487%"靠谱得多
2. **calendar 提效（72%）vs work 提效（77%）**：差 5 点反映"跨夜的代价"——下次试试当天搞定能再提效
3. **person-time vs wall-clock**：单人 Need 两者相同；如果是两人协作，公式分子必须用 person-min 求和
4. **两个独立信号都通过**：ai_code_ratio = 0.79 + uncovered_work_ratio = 0 → 置信度高

## 看完这行字你能想啥？

1. **"72% 提效，AI 让 3.7 天的需求 1 天搞定"** — 这才是业务方真敢拿出去汇报的数字
2. **"实际开发跨度 1.04 天 / 古法估算跨度 3.7 天"** — 两个数字都是含睡眠的 calendar 尺度，可以直接对比
3. **"思考占 42%"** — 你前面想方案的时间跟写代码相当。下次接到类似需求可以更早收敛
4. **"ai_code_ratio = 0.79 + uncovered_work_ratio = 0"** — 两个独立信号都通过：session 内 AI 参与充分，且没有脱离 session 的裸 commit。置信度高的来源

## 换个大需求看看效果

假设这次是个跨 5 天的"重头需求"：
- T_actual_work（5 天累计敲键盘 + 对话） = 24h
- T_baseline_work（古法估算工作时间，三方融合） = 72h
- T_actual_calendar = 5 天 = 120h
- team_work_density = 0.25

```
T_baseline_calendar = 72 / 0.25 = 288h = 12 天

calendar 提效 = 1 - 120 / 288 = 58%

work 提效（内部下钻） = 1 - 24/72 = 67%
```

**业务方解读**："AI 把原本需要 12 天古法工作量的大需求，用 5 天交付，提效 58%"。

注意 calendar 提效（58%）比 work 提效（67%）低 9 个点——大需求跨周末跨夜更多，calendar 上稀释更明显。这反映真实的"日历交付节奏"，不是公式 bug。

## 顺便说一下旧系统这时候在做啥

**双轨并行**。同一份数据，旧系统按 task（一段对话）维度跑老公式 `((ancient - real) / real) * 100`：

- 会话 2 的 ancient = 让 v3 LLM 估"不用 AI 要多久" = 假设 8h（旧系统的 LLM 估也偏低，没用古法系数）
- 会话 2 的 real = 实际 2h
- ratio = ((8 - 2) / 2) × 100 = **300%（提升百分比口径，等价于"提效 300%"）**

老板看了想骂人——这数字明显不可信。但数据保留，作为对照——下次有人质疑"新系统的 72% 是不是太保守"，可以拿出来对比："旧系统给出 300% 你信吗？"

---

## 一句话总结

**把"一个需求"的活儿全捞起来，切三段，三个独立方法估"该多久"，互相校验，给数字 + 区间 + 置信度。**
